# Wrapping the Antigravity CLI is in bounds; borrowing its credentials is not

Antigravity's ToS §6 forbids "using third party software, tools, or services to access the Service", and the February 2026 ban wave hit people who pointed OpenClaw's OAuth plugin at Antigravity credentials so that a *different* agent product could call Google's backend models. CloudCLI does neither: it spawns the official `agy` binary the user installed and authenticated themselves, reads its documented NDJSON on stdout, and never reads, stores or forwards the OAuth tokens `agy` keeps in the OS keyring — architecturally the same shape as Google's own Apache-2.0 Python SDK, which spawns a bundled `localharness` binary and talks to it over a local WebSocket. Accepted for the self-hosted, single-user deployment this fork targets.

**Consequences**: the judgment is scoped to that shape, not to the integration technique. A hosted, multi-user deployment funnelling many users through one Antigravity account reproduces the per-account weekly-quota load pattern Google acted on, and is out of bounds. Re-evaluate before proposing the provider upstream, where the maintainer rather than this fork would carry the risk. The evidence behind every claim here is in `docs/antigravity-agy-provider-feasibility.md`.

**Considered Options**: speaking `antigravity.localharness.*` protobuf to the harness over its local WebSocket, as the Python SDK does — rejected, hand-rolling bindings against an unpublished-for-Node surface is reverse engineering *and* moves toward the pattern §6 objects to, for no capability the CLI's own NDJSON lacks. Registering through `agy remote-control` — rejected, that daemon relays through Google's own service, which is squarely what "third party software accessing the Service" describes.
