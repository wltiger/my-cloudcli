# OpenCode forks through a branch in the client, not through upstream's fork facet

Upstream's fork path cannot take OpenCode as it stands: `IProviderFork.forkSession` requires a `jsonlPath`, and `sessionsService.forkSessionById` refuses any source row without both a `provider_session_id` and a `jsonl_path` (`FORK_SOURCE_NOT_READY`). OpenCode has no such path *on purpose* — every OpenCode session lives in one shared `opencode.db`, so its synchronizer keeps `jsonl_path` null to stop "delete this session's transcript" from deleting every OpenCode conversation on the machine. Adapting OpenCode into the facet therefore means either handing it a path that is a lie or reshaping an upstream-owned contract, so the split lives in the client instead: `useSessionFork` sends a fork to upstream's `POST /sessions/:id/fork` when the provider reports it can be forked there, and to this fork's own `POST /sessions/:id/fork-at-anchor` when it cannot. The branch is keyed on **the provider's upstream fork capability, never on the provider's name** — that is the whole point, because a provider upstream covers later starts reporting the capability and the second branch simply stops being taken, with nothing to edit.

*Why not the Anchor field*: it was at first, and it is not any more. Editing an OpenCode message needs an anchor upstream's Edit path understands, so OpenCode messages now carry `transcriptAnchorId` (for Edit) *and* `anchor` (for Fork) at the same time — which makes "which field does this message carry" unable to say what a Fork of it should do. The capability test is the same deletability property without the ambiguity.

**Delete the branch when** upstream's fork facet stops requiring a transcript path — a nullable/absent `jsonlPath`, or an OpenCode adapter of upstream's own. At that moment this is a pure deletion with no migration: the ternary in `useSessionFork`, the `/fork-at-anchor` route, `session-fork.service.ts`, `opencode-anchors.ts` and `forkOpenCodeSession` all go, and the `anchor` field is left carrying only its remaining job (withholding a gesture at or before a Compact boundary). Nothing persists an anchor, so no stored data points at the removed route.

**Considered Options**: implementing `IProviderFork` for OpenCode and giving its sessions a synthetic `jsonl_path` — rejected, `jsonl_path` is what permanent deletion resolves, so pointing it at the shared database makes deleting one conversation destroy all of them, which is the exact hazard the null was chosen for. Branching on the provider id in `useSessionFork` — rejected, it reads as the honest version of the same thing but has to be edited again the day upstream adds OpenCode, whereas the capability test expires by itself. Widening `forkSessionById` to tolerate a null path — rejected, it is an edit to an upstream-owned service that every future merge would have to defend, for behaviour that is one client-side ternary here; if upstream ever wants it, that is upstream's change to make, not this fork's to carry.
