# On the Claude provider, a turn ending is not the same as a session going idle

Upstream already holds a Claude CLI process open past a turn's `result` so a backgrounded shell or a subagent can keep running and report back (`BG_WAIT_CEILING_MS`), but every consumer of "is this session busy" — the run registry's admission guard, the scheduled-message dispatcher, the frontend's processing map — read a turn's `result` as "done, idle" regardless. That single signal was wrong in both directions at once. Toward the process: the next prompt, or the next scheduled message, was free to supersede and interrupt a session the CLI itself was still using, which is what destroyed background work in the first place ([wltiger/my-cloudcli#51](https://github.com/wltiger/my-cloudcli/issues/51)). Toward the user: a subagent invisible to the runtime's tool-name blacklist made the UI report success while the CLI's own sweep logic was the only thing still protecting it, so nothing distinguished "genuinely finished" from "finished for now, at risk the moment you type again."

The fix does not make the session busy until all background work settles — that would block the one thing the fix exists to enable, a follow-up prompt while background work runs, and the CLI already treats a prompt queued on its main thread as its own "do not sweep, this session is still in use" signal. Instead, "a turn is producing output right now" (turn-in-flight) and "this session has background work outstanding" (background-work-outstanding) are tracked as two independent states. Only turn-in-flight gates a new send — the run registry's admission check, the scheduled-message dispatcher's interrupt behaviour, and the composer's queue gate all read it alone, so a session that's merely holding background work is indistinguishable, at the send gate, from an idle one. Background-work-outstanding is visibility and reachability only: it drives the UI's hold indicator, keeps Stop available and able to reach a process whose run has already completed and been evicted, and keeps the transcript refreshing instead of going silent while a subagent still writes to it.

Background-work-outstanding is a new field on the registry, keyed by session rather than stored on a run, deliberately not a third value inside `ChatRunStatus`. The work it describes outlives the run that started it — that run completes and is evicted after five minutes; the hold can last thirty — so nothing about it belongs to a single run's lifecycle, and every existing `status`-based consumer keeps its current meaning unless it is explicitly pointed at the new field. Whether the flag is set at all comes from the Claude Agent SDK's `Stop`/`SubagentStop` hook snapshot of what's still in flight as a turn wraps up, not from a per-task started/settled tally: a snapshot read fresh at each turn boundary cannot drift the way a counter can when a settle event goes missing, which is a question of "does this ever stay stuck on," not just accuracy.

**Considered Options**: a single busy flag held until background work settles — rejected, it defeats the reuse path this whole effort exists to enable and reintroduces the same "session reads busy or session reads unsafe-to-touch" choice the bug already made wrong. A task-lifecycle counter (increment on start, decrement on settle) — rejected, nothing guarantees a started task's settle event always arrives (a superseded process, an ambient/housekeeping task, a dropped hook registration), so a counter can leak upward and never return to zero, which under a fix that keeps the session busy while it's non-zero means a permanently stuck UI rather than a slow one. Detaching background work to survive independently of the held process (process-group isolation for shells, a standalone lifecycle for subagents) — rejected: a subagent is not a child process to begin with, it is a task inside the CLI process, so there is no "detach" for half the problem, and detaching the half that could be detached gives up the CLI's own result-recovery path (output files, its task registry, its own completion notification) for no reason a user asked for. Folding background-work-outstanding into `ChatRunStatus` as a new enum value — rejected, it would change what every existing `isProcessing()`-shaped call site means without their code changing, turning the scheduled-message dispatcher, the transcript-refresh suppression and the run-admission guard into silent behaviour changes instead of the explicit, one-at-a-time opt-ins a new field gives them.

**Delete this ADR's premise when** upstream implements process reuse and outstanding-work tracking itself — at that point the fork's `claude-turn-reuse.ts` and `claude-background-work.ts` (docs/fork-customizations.md entries 29–30) and the registry/frontend split (entry 31) all retire in favour of upstream's mechanism, since two independent systems pushing prompts into the same held stdin would interleave.
