# Scheduled triggers inherit the session's permission mode and join the approval loop

The fork's scheduled triggers fired headless with an empty allowlist and the provider's *default* permission mode, and the headless writer dropped `permission_request` frames outright — so a trigger that needed a tool the user's interactive mode would have approved hit the wall invisibly: ordinary tools auto-denied after 55s, the trigger was still marked `sent`, and the user saw an incomplete result with no prompt anywhere to answer. A scheduled run had strictly *less* permission than the same prompt typed in the client, which inverts the point of the feature (the spec ticket: [wltiger/my-cloudcli#43](https://github.com/wltiger/my-cloudcli/issues/43)). The fix makes a scheduled run behave like a typed command: `chat.send` records the resolved `permissionMode` the client already sends on every turn onto a new nullable `sessions.permission_mode` column (the same per-send pattern as `model`/`effort`, zero frontend change), the fire path passes the stored value through the existing `permissionMode` runtime option — nothing passed when unset, so the provider default applies — and the headless writer relays `permission_request`/`permission_cancelled` frames to every connected client (remapped to the app session id, since the runtime labels frames with the provider-native id) instead of dropping all of them. Everything downstream of the frame is untouched and writer-independent: the 55s/unbounded timeouts, the `permission.required` push, the `chat_subscribed.pendingPermissions` catch-up, and the `chat.permission-response` resolution — so a scheduled prompt is answerable from any device exactly as an interactive one. The tool allowlist is deliberately *not* persisted or inherited: it is a global browser setting rather than a per-session one, and redundant for completion now that the prompt actually reaches the user. The hard limit is documented, not a defect: "consistent with the client" does not mean "completes unattended" — with no device present a prompt auto-denies after 55s, exactly like a typed prompt left alone, and unattended jobs set the session to `bypassPermissions`, which the trigger then inherits.

**Considered Options**: snapshotting the composer's options (model, effort, permission mode, attachments) at *schedule* time — this is what upstream's `scheduled_messages` module does, in a separate table and code path that a future merge will keep alongside the fork's `scheduled_triggers` — rejected here because the fork's UX promise is "the trigger runs like the session does *now*", and a snapshot would instead pin the trigger to whatever the composer happened to hold when the schedule was drafted. Failing loud — marking the trigger `failed` when its run hits a permission wall — rejected: it turns an answerable prompt into a dead end and redefines what "fired" means in the trigger bookkeeping. Forcing trigger runs into `bypassPermissions` — rejected as the exact inversion the feature exists to fix: it would grant a scheduled run *more* permission than the user's session actually has. A per-trigger mode picker — rejected as UI that encodes a choice the session already makes on every send.
