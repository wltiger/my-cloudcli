# Cache-first app shell with manual refresh, reversing upstream's no-cache-HTML decision

Upstream deliberately never pre-caches `index.html`/the JS bundle in the service worker (`public/sw.js`: "HTML and JS are never pre-cached") and the server sends `no-cache` on HTML specifically "to prevent service worker issues" — avoiding a stale-shell-after-deploy failure mode where cached HTML references JS/CSS asset filenames a new build has already deleted. This fork reverses that decision: the service worker now serves the app shell cache-first (instant load, works fully offline), and picking up a newer shell is a manual action — a Settings button that clears the cache and reloads — rather than automatic network-first freshness checking.

**Considered Options**: network-first with cache fallback (always fresh when online, but doesn't give an instantly-available offline app, which was the actual goal) — rejected in favor of cache-first plus manual refresh. The reintroduced staleness risk is bounded by bumping the cache name (`claude-ui-v2` → `v3`), reusing the existing "delete old-named caches on activate" cleanup — so there is no permanently-stuck-broken-cache scenario, only a stale-until-manually-refreshed one.
