# A committed OpenCode revert is reported, not recovered

OpenCode's Rewind is a revert followed by a send, and the two are not atomic. The ticket that specified it ([#26](https://github.com/wltiger/my-cloudcli/issues/26)) assumed `unrevert` could always put the conversation and the files back if the send failed — true of a **standalone** revert, measured directly. It is not true once the send has started: `opencode run` **commits** an outstanding revert the moment it appends its own user message, physically deleting every reverted message and clearing the session's `revert` state — and that happens well before the model call most failures come from. `unrevert` still answers 200 there, with an empty `revert` indistinguishable from having restored something. The revert was therefore read back before anything was undone, and only a revert **still standing at this Anchor** was taken back. That read-and-undo helper — `undoOpenCodeRewind` — went out with Rewind, and nothing replaced the undo half: `OpenCodeSessionsProvider.rewindSession` now throws when the revert did not land and the gateway ends the run, so nothing is ever sent into a conversation that was never rewound. A committed one is reported for what it is — the earlier messages are gone, the files are still rolled back — and a session that cannot be read at all is reported as unknown rather than as settled. Silent recovery is unacceptable, but a false claim of recovery is worse, and only the read tells them apart.

**Considered Options**: taking CloudCLI's own git snapshot before the revert and restoring from it — rejected, it can only put the *files* back, since OpenCode has already deleted the messages, so it buys half the promise at the price of a working tree that no longer matches the conversation. Deferring the revert until the send is known to have succeeded — rejected as impossible: the revert is the state the send resumes from, which is exactly the atomicity Claude's `resumeSessionAt` gets for free and OpenCode does not. Calling `unrevert` unconditionally and reporting success on its 200 — rejected, and this was the original bug: it told readers their files were back where they were while the rolled-back contents sat on disk.
