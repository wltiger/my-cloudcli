# Fork Customizations

**This fork:** [`wltiger/my-cloudcli`](https://github.com/wltiger/my-cloudcli) (`origin` remote). **Upstream:** [`siteboon/claudecodeui`](https://github.com/siteboon/claudecodeui) (`upstream` remote). `main` tracks `upstream/main` as a clean mirror; all work in this fork — including everything below — lives on `dev`. Full remote/branch/sync setup: `docs/agents/issue-tracker.md`. Step-by-step sync procedure: `docs/upstream-sync.md`.

A living inventory of behavior in this fork (`wltiger/my-cloudcli`) that deliberately diverges from upstream (`siteboon/claudecodeui`). When syncing `upstream/main` and a merge conflict (or a suspicious silent behavior change) lands on one of the files listed below, check the matching entry here before deciding whether to keep this fork's version, reapply it on top of upstream's new code, or drop it because upstream solved the same problem natively.

This is not a TODO list — see the repo's issue tracker (`docs/agents/issue-tracker.md`) for open follow-up work. This file only tracks *that a divergence exists and why*.

Entries marked ❌ retired are no longer in the code. They are kept, unrenumbered, so a later reader can see the divergence once existed and why it went away — usually because upstream solved the same problem. Don't reintroduce one without reading its retirement note first.

## 3. Chat reading appearance settings (spacing / font size / width)

**Files:** `src/components/chat/utils/chatSpacing.ts`, `chatTypography.ts`, `hooks/useChatSpacing.ts`, `useChatTypography.ts`, `view/subcomponents/ChatMessagesPane.tsx`, `MessageComponent.tsx`, `ToolGroupContainer.tsx`, `Markdown.tsx`, `ChatComposer.tsx`, `QueuedMessageCard.tsx`, `chat/tools/components/PlanDisplay.tsx`, `ToolErrorDisplay.tsx`, `ContentRenderers/MarkdownContent.tsx`, `QuestionAnswerContent.tsx`, `InteractiveRenderers/AskUserQuestionPanel.tsx`, `src/components/settings/hooks/useSettingsController.ts`, `settings/view/Settings.tsx`, `settings/view/tabs/AppearanceSettingsTab.tsx`, `src/components/quick-settings-panel/view/QuickSettingsContent.tsx`, `ForkQuickSettings.tsx`, `QuickSettingsChatSpacingRow.tsx`, `QuickSettingsChatFontRow.tsx`, `QuickSettingsChatWidthRow.tsx`, `src/i18n/locales/{en,zh-CN}/settings.json`

**Why:** Three knobs over how the chat reads, sharing one storage-plus-event pattern and one pair of surfaces (the Settings modal's Appearance tab and the Quick Settings panel). All three default to upstream's current values, so an untouched install looks exactly like upstream.

- **Message spacing** (Spacious/Compact/None, mobile-only): small phone screens waste space on the fixed horizontal padding around chat bubbles. Because the setting is a no-op above the `sm:` breakpoint, the Quick Settings row keeps a short note saying it only affects narrow screens — rather than hiding the row on desktop, which reads as the setting having disappeared.
- **Reading font size** (Small/Medium/Large/X-Large → `prose-sm`/`prose-base`/`prose-lg`/`prose-xl`, default Small = upstream's 14px): upstream's body text is small on a large monitor, and AskUserQuestion is worse — its inline option *description* is 11px. The level covers **reading text only**: Markdown body (messages, Plan, tool errors, tool markdown results) and AskUserQuestion's question/option/description text. Code blocks, diffs, tool card summary lines, timestamps and badges deliberately keep their sizes — the code editor already has its own `codeEditorFontSize`. AskUserQuestion's existing fullscreen sizes (19/18/15px) stay fixed, and every inline level stays strictly below them so inline can never out-size fullscreen.
- **Content width** (Standard/Wide/Wider/Full, default Standard = upstream's `max-w-[54.25rem]`): with the fixed 288px sidebar, an 868px column uses 38% of a 2560px screen and 28% of a 3440px one. The user bubble's top cap (`xl:max-w-xl`) follows the level too, so a 576px bubble isn't stranded in a 3000px column. Only that top step moves: below `xl` the column hasn't reached its own cap yet, so `sm:max-w-[85%] md:max-w-md lg:max-w-lg` still describes it better than a percentage — a blanket `max-w-[66%]` would actually *shrink* the bubble at `md` (448px column, where it currently fills the width). Each level's value is ~66% of that level's column, which is what `xl:max-w-xl` already worked out to at the standard width, so Standard is byte-identical to before.

Design notes worth keeping: `Markdown.tsx` is the single funnel for the prose level (call sites just drop their `prose-sm`; an explicitly passed size such as fullscreen's `prose-lg` still wins), and CSS `zoom` was rejected as the scaling mechanism because `useComposerMenuAnchor.ts` computes fixed-position menu coordinates from `getBoundingClientRect()` + `window.innerWidth`, which a `zoom` ancestor breaks. Tracked as one customization across all its iterations. Ticket: [#17](https://github.com/wltiger/my-cloudcli/issues/17).

**On upstream conflict:** Keep mine. Pure opt-in settings, additive. In `QuickSettingsContent.tsx` the whole fork footprint is two lines — a `ForkQuickSettings` import and a `<ForkQuickSettings />` appended as the panel body's last child. Every fork-added quick setting lives inside `ForkQuickSettings.tsx` (a file upstream doesn't have), so reapplying after a conflict means restoring those two lines and nothing else; do not push new rows back into upstream's own sections. The column `max-w` is duplicated across `ChatMessagesPane.tsx`, `ChatComposer.tsx` (three sites) and `QueuedMessageCard.tsx` — if upstream changes one of them, all of them must stay in sync or the composer stops lining up with the message list.

⚠️ **i18n policy changed here.** This entry used to state that all strings use `t(key, 'English default')` fallbacks with no `src/i18n/locales/**` edits, keeping translation files a zero-conflict surface. That no longer holds: `en` and `zh-CN` `settings.json` now carry the `appearanceSettings.chatSpacing` / `chatFontSize` / `chatWidth` keys, so the Chinese UI is complete. A fork-only i18n namespace was considered as a zero-conflict alternative and rejected — `src/i18n/config.js` hardcodes every namespace's import, `resources` entry and `ns` entry, making a new namespace a *larger* conflict surface than additive JSON keys. On conflict in those two files, keep both sides' keys; the other nine locales are still untouched and fall back to the inline English defaults.

## 5. Offline-capable app shell (service worker cache-first) ⚠️ re-evaluate, don't blindly keep

**Files:** `public/sw.js`, `src/components/settings/view/tabs/AboutTab.tsx`

**Why:** CloudCLI ships PWA infrastructure but didn't actually work offline — the service worker deliberately never cached the HTML/JS shell, and the server sends `no-cache` on HTML specifically "to prevent service worker issues." This fork reverses that decision: cache-first app shell + a manual "Refresh offline cache" control, no automatic staleness detection.

**On upstream conflict:** **Highest-priority re-check in this list.** This directly reverses an intentional upstream design choice. If upstream ever touches `public/sw.js` or the `Cache-Control` headers in `server/index.ts`, re-read `docs/adr/0002-cache-first-app-shell-manual-refresh.md` before reapplying — upstream may have addressed the exact staleness failure mode that made them avoid this in the first place, which would change the tradeoff.

## 10. Web Push VAPID subject that APNs accepts

**Files:** `server/modules/notifications/vapid-keys.service.ts`

**Why:** Upstream hardcodes `mailto:noreply@claudecodeui.local` as the VAPID `sub` claim. `.local` is a reserved TLD, and APNs validates that claim — it rejects every push with `403 BadJwtToken`, so **no iOS device has ever received a notification**. Verified against a live install with a real Home Screen web app subscription: same subscription, same keys, only the subject changed — `.local` → 403, `https://cloudcli.ai` → 201, a real `mailto:` → 201. Chrome's FCM and Mozilla's Autopush don't validate the domain, which is why the breakage is iOS-only and went unnoticed upstream.

**On upstream conflict:** Take upstream's version if they've fixed it themselves — any routable `mailto:`/`https:` value works, the specific string doesn't matter. Otherwise keep mine and reapply. **Triaged and deliberately not reported** — see `docs/pull-requests/PR01-vapid-subject-ios-push.md`. It is severe (no iOS device has ever received a push from an unmodified install) and one line to fix, but it costs this fork nothing, which is the test that decides these. Don't reopen the question on severity grounds; that argument was already made and rejected. Once upstream ships an equivalent fix this entry can be dropped.

## 14. Browser runtime installs into a managed directory

**Files:** `server/modules/browser-use/browser-use.service.ts`

**Why:** Upstream's `installRuntime()` runs `npm install --no-save --no-package-lock playwright` with `cwd: process.cwd()`, but `getPlaywright()` resolves `require('playwright')` from the module's own location. For a globally installed CloudCLI those are two different trees: the install lands in whatever directory the user happened to launch the CLI from (often the home directory), which node never walks into when resolving from `<npm root -g>/@cloudcli-ai/cloudcli/dist-server/server/modules/browser-use/`. So the install genuinely succeeds, the Settings tab still reports `Playwright: missing`, and the "Install Runtime" button looks like it does nothing no matter how often it is clicked — each click just reinstalls into the same unreachable place. Installing now targets `~/.cloudcli/browser-use/runtime` (beside the existing `profiles/` dir), seeded with a private `package.json` so npm does not walk up and adopt whatever project sits above it, and `getPlaywright()` tries the module's own resolution first and that directory second. `runCommand()` took a `cwd` argument for this. Dropping `--no-save --no-package-lock` is safe now that the manifest is fork-owned, and keeping the lockfile makes reinstalls cheaper.

**On upstream conflict:** This is a plain bug fix rather than a fork preference. **Already reported upstream by others** — [#995](https://github.com/siteboon/claudecodeui/pull/995) proposes an identical fix (same `~/.cloudcli/browser-use/runtime` directory, same resolve-order), with [#1000](https://github.com/siteboon/claudecodeui/pull/1000) and [#917](https://github.com/siteboon/claudecodeui/pull/917) covering the same root cause; all three open and unanswered since June–July 2026. Don't file a fourth (see `docs/pull-requests/PR04-browser-runtime-install-directory.md`). If any of them merges, take upstream's version and retire this entry. Until then keep mine, but treat `installRuntime()` and `getPlaywright()` as a pair: they only work together, so if upstream rewrites either one, reapply both halves rather than merging one side and leaving the other. If upstream instead solves it by shipping playwright as a real dependency, drop this entirely — the first resolver already covers that case.

## 15. Tab switcher collapses into a menu on mobile

**Files:** `src/components/main-content/view/subcomponents/MainContentTabMenu.tsx`, `MainContentTabSwitcher.tsx`, `MainContentHeader.tsx`, `src/shared/view/ui/ActionMenu.tsx`

**Why:** Upstream puts the header title and the tab pills on one row. Below `lg:` the pills are already icon-only, but the count is not fixed — 4 built-ins plus optional Browser and Tasks plus one per enabled plugin — so on a 375px phone the strip takes ~148–220px and the title is left with under 150px (measured 51px with 6 tabs). Upstream's own mitigation, a horizontal scroller with gradient fade masks, stops the overflow but hands the title no width back. That costs more in this fork than upstream because entry 13 turned the chat title into the cross-project session switcher, so squeezing it also squeezes a navigation entry point. Measured title width went 51px → 217px. Desktop is untouched, scroller and fade masks included.

**On upstream conflict:** Keep mine. The upstream footprint is deliberately tiny and purely additive: one prop plus one early `return` in `MainContentTabSwitcher.tsx`, one prop pass-through in `MainContentHeader.tsx`, and four optional props on `ActionMenu` (`triggerIcon`, `showChevron`, item `iconNode`, item `isActive`) that its two existing call sites never set. All the menu code lives in the fork-owned `MainContentTabMenu.tsx`, so reapplying means restoring those spots. The early `return` sits *after* the tab list is built on purpose — both renderings share one list, so a built-in tab added upstream shows up in the mobile menu for free; keep that ordering when reapplying. The dropdown uses `ActionMenu`'s `portal` mode deliberately: the header's tab slot is `overflow-hidden` and would clip an absolutely-positioned menu, so if upstream restructures that wrapper, re-check the clipping before switching away from portal. Strings use `t(key, { defaultValue })`, no `src/i18n/locales/**` edits (same as entries 3 and 13). If upstream ships its own mobile tab affordance, take theirs and drop this. ⚠️ v1.37.2 moved in that direction without going all the way: the tab bar is now a proper scroller (edge fades, desktop arrow buttons, wheel-to-scroll, keyboard `role="tab"` navigation) and on mobile shows the label only on the active tab. That is still a scroller, not a collapse, so it does not reclaim title width and this entry was kept — but re-evaluate it on a real phone rather than reapplying blindly next sync.

⚠️ **`MainContentHeader.tsx` now needs an `isMobile` branch on the layout itself, not just the pass-through prop.** v1.37.2 also restructured the header to `flex-col … sm:flex-row`, stacking the title and the tab strip on their own rows below `sm:` so the full-width scroller gets a row to itself. Taking that verbatim put the fork's single compact pill on a row of its own — 81px of header instead of 45px, and the title back to a fraction of the width, i.e. the exact opposite of this entry's purpose. The merged header therefore keeps upstream's classes for the desktop branch and uses `flex-row items-center` plus `shrink-0` (no `-mx-3` edge bleed, that's for the scroller) when `isMobile`. If upstream restructures the header again, re-check that the pill still shares the title's row.

This was missed by a browser check at 700px and caught later on a real phone: `isMobile` is `<768px` but Tailwind's `sm:` is `640px`, so the 640–768px band renders the fork's pill *and* upstream's single-row layout and looks correct. **Test mobile layout at ~390px, not just "a narrow window"** — a viewport between two thresholds can satisfy both branches at once and hide the bug. Note entry 13's cross-project switcher is retired, so the "squeezing a navigation entry point" half of the rationale above no longer applies.

## 16. Push notifications collapse to one-per-session, cleared on open or once resolved elsewhere

**Files:** `server/modules/notifications/services/notification-orchestrator.service.js`, `server/modules/notifications/index.ts`, `server/modules/providers/list/claude/claude-runtime.provider.js`, `public/sw.js`, `src/components/app/AppContent.tsx`

**Why:** Upstream tags each push `provider:sessionId:code`, so a session that fires a permission request, then a stop, then an error keeps three separate notifications stacked in the phone's notification center forever — none of them ever gets cleared, including the ones you already acted on inside the app. This fork drops `code` from the tag when a `sessionId` is present (`provider:sessionId`). The obvious mechanism — the OS replacing same-tag notifications on its own (`renotify: true`) — turned out to only work on Chrome/Android: iOS Safari never replaces same-tag notifications (verified against a real device; matches [WebKit bug 258922](https://bugs.webkit.org/show_bug.cgi?id=258922)), so `sw.js`'s `push` handler now closes any already-shown notification for the same `sessionId` itself (`closeSessionNotifications()`) before calling `showNotification()`, rather than relying on the browser to do it. Opening that session in the app additionally posts `{ type: 'CLEAR_SESSION_NOTIFICATIONS', sessionId }` to the service worker, reusing the same close helper — this is what catches the case where the tag/session-collapse path was bypassed. Sessionless events (e.g. `push.enabled`) keep a `provider:global:code` tag so they don't collapse into each other. Separately: answering a permission request (including AskUserQuestion) on one device left the same request's push notification stuck on every *other* subscribed device, since nothing told them it had been resolved. `chat.permission-response` already resolves through provider-neutral `resolveToolApproval()` regardless of which client sent it, so that function now also fires `notifyPermissionResolved()` — a real, spec-compliant push (not a silent/data-only one, which risks the browser treating the subscription as abusive and revoking it) with code `permission.resolved` reusing the same session tag, which collapses the stale "action required" notification into a "handled" one everywhere via the mechanism above. ## 20. Scheduled session triggers (send a message later)

**Files:** `server/modules/database/schema.ts`, `server/modules/database/index.ts`, `server/modules/database/repositories/scheduled-triggers.db.ts`, `server/modules/scheduled-triggers/` (new module: `index.ts`, `scheduled-triggers.routes.ts`, `services/scheduled-trigger.service.ts`, `services/scheduler-poller.service.ts`, `tests/`), `server/index.ts`, `server/modules/notifications/services/notification-orchestrator.service.js`, `.env.example`, `src/utils/api.js`, `src/components/chat/hooks/useScheduledTrigger.ts`, `src/components/chat/view/subcomponents/ComposerScheduleMenu.tsx`, `ChatComposer.tsx`, `src/components/chat/view/ChatInterface.tsx`, `src/i18n/locales/en/chat.json`

**Why:** Some Codex/Claude relays (third-party API resellers) enforce their own rate-limit windows and return a plain-text error naming a clock time to retry after (e.g. `请在 今天 15:00 后再试`) instead of a structured `retry-after`. Upstream has no notion of "wait, then resend" at all — a rate-limited session just sits there until the user manually comes back and retypes. This adds a generic, provider-agnostic "schedule a message" primitive: any session can queue a one-shot future message (defaulting to `continue`, editable) via a new clock-icon composer menu; a 30s backend poller fires it through the same `providerRuntimeService.run()` seam `chat.send` and the headless `/api/agent` route already share, so no provider gets special-cased.

The poller claims a trigger (`pending` → `firing`) *before* calling the provider, not after — the first version marked it fired only on success, so a provider call slower than one poll interval got re-picked-up and fired again by the next tick (observed firsthand: a slow response sent the same `"continue"` into a live session repeatedly). A trigger stuck `firing` from a crash mid-fire is reset to `pending` on the next boot so it isn't lost forever, just retried.

The composer UI is time-only — no date picker at all. A bare `HH:mm` always means "the next occurrence of that clock time": today if it hasn't passed yet, tomorrow (at most 24h out) otherwise — computed fresh on every render, not decided once and stored. An earlier version *did* store that decision on the input's `onChange`, and a native time input fires `onChange` once per segment as you type (hour, then minute) rather than once when you're done; a not-yet-finished intermediate value could permanently latch onto "tomorrow" mid-edit even though the value you finished typing was still later today. A plain, non-interactive "Tomorrow" label appears next to the input when applicable; there's deliberately no way to pick an arbitrary date. Five presets cover the common cases: `+10min`/`+60min` (stack — each click adds to whatever's currently drafted, not to "now"), the next on-the-hour mark, the next `{0,3,6,9,12,15,18,21}` mark, and a fixed `00:05` "first thing tomorrow" shortcut. Reopening the popover always resets to a fresh default rather than whatever was left over from a previous open/schedule/cancel.

Deliberately scoped to a manual, one-shot primitive for this pass — automatically detecting a relay's rate-limit text and auto-creating a trigger from it is an intentionally deferred follow-up, not built here. Fires headlessly (no live WebSocket client attached), so an already-open chat tab does not see the reply stream in — it only learns the session changed via a `session_upserted` ping, which the frontend already treats as sidebar-only; genuinely live-streaming a headless-fired run into an open tab is unaddressed. Missed triggers (server down at `trigger_at`) fire late within a configurable grace window (`SCHEDULED_TRIGGER_GRACE_WINDOW_MINUTES`, default 60) and are marked `expired` beyond it, rather than either silently dropping or firing an arbitrarily stale message.

**On upstream conflict:** Keep mine. New table + new module, near-zero conflict surface on its own; the only edits to files upstream also owns are additive (one `CREATE TABLE IF NOT EXISTS` block + two indexes appended to `INIT_SCHEMA_SQL` in `schema.ts`, one repository export line in `database/index.ts`, two route-mount/poller-start lines plus one import in `server/index.ts`, one `ComposerScheduleMenu` slot in `ChatComposer.tsx` next to the existing `ComposerPermissionMenu`, one `sessionId` prop threaded from `ChatInterface.tsx`, two new `CODE_MAP` entries in the notification orchestrator). If upstream touches `chat-websocket.service.ts`'s `runtimeOptions` construction (`cwd`/`projectPath` from the session row), mirror the same shape in `scheduled-trigger.service.ts`'s `fireTrigger()` — it was deliberately copied from there rather than factored into a shared helper. If upstream ever adds a real "resend into an open tab" push mechanism, reuse it here instead of the current `session_upserted`-only ping.

## 21. Wide markdown tables scroll instead of squeezing

**Files:** `src/components/chat/view/subcomponents/Markdown.tsx`

**Why:** Upstream's table renderer pairs an `overflow-x-auto` wrapper with a `min-w-full` table. CSS auto table layout only overflows its container when the content *cannot* wrap any further, so a table of ordinary prose compresses each column down toward its longest single word rather than overflowing — the wrapper gets nothing to scroll and the text becomes unreadable. Adding `w-max` lets the table take its natural width so the wrapper actually scrolls, `min-w-28`/`max-w-[22rem]` on `th`/`td` keep individual columns from collapsing or running away, and `overscroll-x-contain` stops a horizontal swipe inside the table from chaining out to the page behind it.

**On upstream conflict:** Not a fork preference — a plain bug fix, but **triaged and deliberately not reported** (see `docs/pull-requests/PR03-markdown-table-horizontal-scroll.md`: upstream had just restyled these lines, and the width bounds are this fork's untested tuning). Drop this entry if upstream fixes it themselves. Until then keep mine, but merge rather than replace: v1.37.2 restyled these same lines (rounded bordered wrapper, borderless cells, `my-0` to cancel Tailwind Typography's table margin) and taking the fork's side wholesale would have silently reverted all of that. Take upstream's classes and re-add the four width/overscroll classes on top.

Ticket [#22](https://github.com/wltiger/my-cloudcli/issues/22); this is the tracer bullet for a five-ticket set ([#23](https://github.com/wltiger/my-cloudcli/issues/23) OpenCode fork, [#24](https://github.com/wltiger/my-cloudcli/issues/24) Clear, [#25](https://github.com/wltiger/my-cloudcli/issues/25) Claude rewind, [#26](https://github.com/wltiger/my-cloudcli/issues/26) OpenCode rewind), so most of what landed here is the seam those tickets attach to rather than the button itself.

The load-bearing decision is that **an Anchor is computed on the backend and shipped with each message**, as a new optional `anchor` field on `NormalizedMessage`. It cannot be derived on the frontend: `normalizeMessage` mints composite ids (`${baseId}_tr_${tool_use_id}`, `${baseId}_text_${partIndex}`, `${baseId}_text`, `${baseId}_images`), so what the frontend holds is never a clean transcript uuid — and one rendered message is not one transcript row anyway. `claude-anchors.ts` — a fork-owned pure function, `buildClaudeAnchorIndex(rows)` — takes the raw JSONL rows and returns row-uuid → anchor-uuid, and `fetchHistory` stamps each normalized message with the anchor of the row it came from. Three measured facts shape it, all confirmed against real transcripts and SDK 0.3.165 rather than read from docs: (1) one agent turn is written as several rows — reasoning, text, one per tool call — sharing the same `message.id`, and `forkSession`'s `upToMessageId` is **inclusive**, so a turn's anchor is its **last** row; anchoring at the first row silently truncates the turn. (2) Those rows are **not necessarily adjacent**: an assistant message issuing two tool calls has each tool result written between its two `tool_use` rows, so the grouping is by `message.id` across the whole transcript, not by consecutive run — a run-based grouping passes the simple case and quietly splits the parallel-tool case. (3) Every row up to and including the **last compaction boundary** gets no anchor at all, so the frontend offers no entry there: a Rewind anchor from before a Compact is known to fail hard (`resumeSessionAt` → `No message found with message.uuid of: …`), Fork's tolerance was never measured, and the conservative rule applies to both. Observed live on a session with two `/compact` runs: every message at or before the boundary came back with no anchor, the one after it carried one.

Fork itself is a **pure file operation** — the SDK copies the transcript, remaps every uuid, preserves the parent chain, writes `<newSessionId>.jsonl` next to the original in the same project directory, and neither runs the model nor costs tokens. `dir` is the *workspace* path, the same value the session row stores as `project_path`, not the `~/.claude/projects/...` folder. Because uuids are remapped, the fork's own anchors are recomputed from its own file and differ from the source's — which is exactly why an anchor is never persisted anywhere.

The provider seam is one **optional** method, `forkSession?`, appended to `IProviderSessions`, deliberately rather than a per-provider `if` inside the service: providers disagree about whether the anchored row is kept or dropped (OpenCode's fork excludes it while its own revert includes it), so each implementation owns that, and #23/#26 add theirs the same way. `session-fork.service.ts` owns everything provider-independent: it resolves the provider through `providerRegistry`, calls the facet, then registers the copy. Registration is three `sessionsDb` calls and each is load-bearing — `createAppSession` (app-allocated id + the fork's name), `assignProviderSessionId` (records the mapping, merging the row the watcher may already have created), then `createSession(...)` purely to write `jsonl_path`, which is exactly what the sessions watcher would do on its next pass and which the fork needs *now* or it opens looking empty. The app-session shape (`session_id` ≠ `provider_session_id`) is not cosmetic: `createSession`'s `custom_name` CASE only preserves a name when those two differ, so registering the fork under its provider id instead would let the next synchronizer pass overwrite `[Fork] …` with a title derived from the first user prompt. Model and reasoning effort are copied from the source row so the fork resumes with the same runtime configuration.

The naming dialog is pre-filled with `[Fork] <original name>`, sequence-numbered (`(2)`, `(3)`, gaps filled) when that name is already taken in the same project, archived sessions included. That suggestion is resolved on the **backend** (`GET /sessions/:sessionId/fork-name`) because the frontend's project payloads are paginated and only hold the first page of names, so it cannot tell what is taken; the hook fetches it *before* opening the dialog, so the input is never briefly empty or briefly wrong. `buildForkSessionName` is exported purely so the naming rule is pinned by tests. Nothing is created until confirm — verified: cancelling left zero rows and zero new transcript files.

On the frontend, `supportsFork` follows the `supportsCompact` precedent from entry 22 exactly, including its **no-fallback** rule: `getSupportsForkForProvider` reads false for every provider until `/api/providers/capabilities` resolves, so the entry stays hidden rather than briefly appearing for a provider that cannot fork. There is no per-provider branching anywhere in `src/` — a message either carries an `anchor` or it does not. `anchor` rides through `useChatMessages.ts`'s `sharedMetadata`, the one object spread into every emitted message kind, rather than through a per-kind `case`, because it applies to all of them. The entry is also hidden while a run is in flight (`!isProcessing`), which happens to cover the one real gap: **live-streamed messages carry no anchor**, because a turn's anchor is not knowable until that turn's last row exists. This self-heals rather than needing code — the sessions watcher sees the transcript change, the chat pane reloads history, and the finished turn gains its anchor; observed directly by sending a message into a fork and watching the new turn become forkable seconds later. Confirming a fork switches the UI through `handleSessionEstablished`, the same handoff a brand-new session uses, so the sidebar picks it up without a second parallel path; the fork is renamed afterwards through the sidebar's existing inline rename, and no second rename was built.

A **prefactor** shipped with this and is worth knowing on its own: `claude-sessions.provider.ts` had a module-local `async function getSessionMessages(...)` whose name collides with the SDK's own `getSessionMessages` export that #25 needs to import into this same file (see ADR 0007). It is renamed to `readClaudeTranscriptRows`, which also just describes it better.

**On upstream conflict:** Keep mine. Upstream has no Fork, no Anchor, and no per-message action beyond copy/speak/fullscreen, so the great majority of this is net-new code in net-new files that can never conflict.
