# Fork Customizations

**This fork:** [`wltiger/my-cloudcli`](https://github.com/wltiger/my-cloudcli) (`origin` remote). **Upstream:** [`siteboon/claudecodeui`](https://github.com/siteboon/claudecodeui) (`upstream` remote). `main` tracks `upstream/main` as a clean mirror; all work in this fork — including everything below — lives on `dev`. Full remote/branch/sync setup: `docs/agents/issue-tracker.md`. Step-by-step sync procedure: `docs/upstream-sync.md`.

A living inventory of behavior in this fork (`wltiger/my-cloudcli`) that deliberately diverges from upstream (`siteboon/claudecodeui`). When syncing `upstream/main` and a merge conflict (or a suspicious silent behavior change) lands on one of the files listed below, check the matching entry here before deciding whether to keep this fork's version, reapply it on top of upstream's new code, or drop it because upstream solved the same problem natively.

This is not a TODO list — see the repo's issue tracker (`docs/agents/issue-tracker.md`) for open follow-up work. This file only tracks *that a divergence exists and why*.

Entries marked ❌ retired are no longer in the code. They are kept, unrenumbered, so a later reader can see the divergence once existed and why it went away — usually because upstream solved the same problem. Don't reintroduce one without reading its retirement note first.

## 3. Chat reading appearance settings (spacing / font size / width)

**Files:** `src/shared/chatSpacing.ts` (+ `src/shared/tests/chatSpacing.test.ts`), `src/shared/chatTypography.ts`, `src/shared/hooks/useChatSpacing.ts`, `src/shared/hooks/useChatTypography.ts`, `.oxlintrc.json` (the two new `src/shared/*.ts` files must be listed under `boundaries/elements` → `frontend-shared-file`, or `boundaries/no-unknown` errors), `src/modules/chat/transcript/ChatMessagesPane.tsx`, `MessageComponent.tsx`, `ToolGroupContainer.tsx`, `Markdown.tsx`, `StreamingMarkdown.tsx`, `src/modules/chat/composer/ChatComposer.tsx`, `QueuedMessageCard.tsx`, `src/modules/chat/tools/PlanDisplay.tsx`, `ToolErrorDisplay.tsx`, `ContentRenderers/MarkdownContent.tsx`, `QuestionAnswerContent.tsx`, `InteractiveRenderers/AskUserQuestionPanel.tsx`, `src/modules/settings/hooks/useSettingsController.ts`, `src/modules/settings/Settings.tsx`, `src/modules/settings/tabs/AppearanceSettingsTab.tsx`, `src/modules/quick-settings-panel/QuickSettingsContent.tsx`, `ForkQuickSettings.tsx`, `QuickSettingsChatSpacingRow.tsx`, `QuickSettingsChatFontRow.tsx`, `QuickSettingsChatWidthRow.tsx`, `src/modules/i18n/locales/{en,zh-CN}/settings.json`

**Why:** Three knobs over how the chat reads, sharing one storage-plus-event pattern and one pair of surfaces (the Settings modal's Appearance tab and the Quick Settings panel). All three default to upstream's current values, so an untouched install looks exactly like upstream.

- **Message spacing** (Spacious/Compact/None, mobile-only): small phone screens waste space on the fixed horizontal padding around chat bubbles. Because the setting is a no-op above the `sm:` breakpoint, the Quick Settings row keeps a short note saying it only affects narrow screens — rather than hiding the row on desktop, which reads as the setting having disappeared.
- **Reading font size** (Small/Medium/Large/X-Large → `prose-sm`/`prose-base`/`prose-lg`/`prose-xl`, default Small = upstream's 14px): upstream's body text is small on a large monitor, and AskUserQuestion is worse — its inline option *description* is 11px. The level covers **reading text only**: Markdown body (messages, Plan, tool errors, tool markdown results) and AskUserQuestion's question/option/description text. Code blocks, diffs, tool card summary lines, timestamps and badges deliberately keep their sizes — the code editor already has its own `codeEditorFontSize`. AskUserQuestion's existing fullscreen sizes (19/18/15px) stay fixed, and every inline level stays strictly below them so inline can never out-size fullscreen.
- **Content width** (Standard/Wide/Wider/Full, default Standard = upstream's `max-w-[54.25rem]`): with the fixed 288px sidebar, an 868px column uses 38% of a 2560px screen and 28% of a 3440px one. The user bubble's top cap (`xl:max-w-xl`) follows the level too, so a 576px bubble isn't stranded in a 3000px column. Only that top step moves: below `xl` the column hasn't reached its own cap yet, so `sm:max-w-[85%] md:max-w-md lg:max-w-lg` still describes it better than a percentage — a blanket `max-w-[66%]` would actually *shrink* the bubble at `md` (448px column, where it currently fills the width). Each level's value is ~66% of that level's column, which is what `xl:max-w-xl` already worked out to at the standard width, so Standard is byte-identical to before.

Design notes worth keeping: `useChatProseClassName()` is the single funnel for the prose level (call sites just drop their `prose-sm`; an explicitly passed size such as fullscreen's `prose-lg` still wins). It used to live inside `Markdown.tsx`, but v1.37.3 split the transcript's markdown in two — an assistant reply now renders through `StreamingMarkdown`, which owns *its own* prose container instead of `Markdown`'s — so the funnel moved into `useChatTypography.ts` and both containers call it. Wiring only `Markdown` would leave every assistant message stuck at the default size, which is the one case the setting is actually for. CSS `zoom` was rejected as the scaling mechanism because `useComposerMenuAnchor.ts` computes fixed-position menu coordinates from `getBoundingClientRect()` + `window.innerWidth`, which a `zoom` ancestor breaks. Tracked as one customization across all its iterations. Ticket: [#17](https://github.com/wltiger/my-cloudcli/issues/17).

**These four files live in `src/shared/`, not in the chat module — do not move them back.** They started under `src/modules/chat/`, and v1.37.3's lint-enforced barrel rule (`boundaries/dependencies`) then forced settings and quick-settings-panel to reach them through `src/modules/chat/index.ts`. That barrel's first line is `export { default as ChatInterface }`, and ESM evaluates a module's whole body for any named import, so importing one 40-line hook pulled in ~337 modules — the entire chat UI, and through it xterm (`ChatInterface` → task-master barrel → `TaskMasterSetupModal` → shell barrel, and again via `provider-auth` → `standalone-shell`). That broke `src/modules/settings/tests/settingsControllerCodeEditor.test.ts` under vitest+jsdom: 8.9s of module transforms against a 5s test timeout, plus `HTMLCanvasElement.prototype.getContext` errors from xterm's module-scope canvas probe. Three feature modules use these hooks, so `src/shared/hooks/` is where `.agents/skills/frontend-module-standards/SKILL.md` puts them anyway ("Put a hook used by multiple feature modules in `src/shared/hooks/`"), and it removes the settings→chat module edge entirely. Re-exporting them from the chat barrel again would bring the failure straight back.

**On upstream conflict:** Keep mine. Pure opt-in settings, additive. In `QuickSettingsContent.tsx` the whole fork footprint is two lines — a `ForkQuickSettings` import and a `<ForkQuickSettings />` appended as the panel body's last child. Every fork-added quick setting lives inside `ForkQuickSettings.tsx` (a file upstream doesn't have), so reapplying after a conflict means restoring those two lines and nothing else; do not push new rows back into upstream's own sections. The column `max-w` is duplicated across `ChatMessagesPane.tsx`, `ChatComposer.tsx` (three sites) and `QueuedMessageCard.tsx` — if upstream changes one of them, all of them must stay in sync or the composer stops lining up with the message list. (A fifth site, `SessionRewindNotice.tsx`, went away with Rewind in v1.37.3; upstream's editing notice lives inside `ChatComposer.tsx` and is already covered by those three.)

⚠️ **i18n policy changed here.** This entry used to state that all strings use `t(key, 'English default')` fallbacks with no `src/i18n/locales/**` edits, keeping translation files a zero-conflict surface. That no longer holds: `en` and `zh-CN` `settings.json` now carry the `appearanceSettings.chatSpacing` / `chatFontSize` / `chatWidth` keys, so the Chinese UI is complete. A fork-only i18n namespace was considered as a zero-conflict alternative and rejected — `src/modules/i18n/config.ts` hardcodes every namespace's import, `resources` entry and `ns` entry, making a new namespace a *larger* conflict surface than additive JSON keys. On conflict in those two files, keep both sides' keys; the other nine locales are still untouched and fall back to the inline English defaults.

## 5. Offline-capable app shell (service worker cache-first) ⚠️ re-evaluate, don't blindly keep

**Files:** `public/sw.js`, `src/modules/settings/tabs/AboutTab.tsx`

**Why:** CloudCLI ships PWA infrastructure but didn't actually work offline — the service worker deliberately never cached the HTML/JS shell, and the server sends `no-cache` on HTML specifically "to prevent service worker issues." This fork reverses that decision: cache-first app shell + a manual "Refresh offline cache" control, no automatic staleness detection.

**On upstream conflict:** **Highest-priority re-check in this list.** This directly reverses an intentional upstream design choice. If upstream ever touches `public/sw.js` or the `Cache-Control` headers in `server/index.ts`, re-read `docs/adr/0002-cache-first-app-shell-manual-refresh.md` before reapplying — upstream may have addressed the exact staleness failure mode that made them avoid this in the first place, which would change the tradeoff.

**Files:** `vite.config.js`, `src/vite-env.d.ts`, `src/modules/settings/tabs/AboutTab.tsx`, `server/index.ts`

**Why:** With the offline cache-first shell (#5) it became hard to tell whether a running instance is a fresh build or a stale cached one. Shows the build's git SHA + timestamp next to the version badge, front and back.

## 10. Web Push VAPID subject that APNs accepts

**Files:** `server/modules/notifications/vapid-keys.service.ts`

**Why:** Upstream hardcodes `mailto:noreply@claudecodeui.local` as the VAPID `sub` claim. `.local` is a reserved TLD, and APNs validates that claim — it rejects every push with `403 BadJwtToken`, so **no iOS device has ever received a notification**. Verified against a live install with a real Home Screen web app subscription: same subscription, same keys, only the subject changed — `.local` → 403, `https://cloudcli.ai` → 201, a real `mailto:` → 201. Chrome's FCM and Mozilla's Autopush don't validate the domain, which is why the breakage is iOS-only and went unnoticed upstream.

**On upstream conflict:** Take upstream's version if they've fixed it themselves — any routable `mailto:`/`https:` value works, the specific string doesn't matter. Otherwise keep mine and reapply. **Triaged and deliberately not reported** — see `docs/pull-requests/PR01-vapid-subject-ios-push.md`. It is severe (no iOS device has ever received a push from an unmodified install) and one line to fix, but it costs this fork nothing, which is the test that decides these. Don't reopen the question on severity grounds; that argument was already made and rejected. Once upstream ships an equivalent fix this entry can be dropped.

**Files:** `src/modules/file-tree/FileContextMenu.tsx`, `FileTreeNode.tsx`, `FileTreeList.tsx`, `FileTreeBody.tsx`, `FileTree.tsx`, `src/modules/file-tree/hooks/useFileTreeOperations.ts`, `utils/fileTreeUtils.ts`, `src/modules/i18n/locales/*/common.json`

## 14. Browser runtime installs into a managed directory

**Files:** `server/modules/browser-use/browser-use.service.ts`

**Why:** Upstream's `installRuntime()` runs `npm install --no-save --no-package-lock playwright` with `cwd: process.cwd()`, but `getPlaywright()` resolves `require('playwright')` from the module's own location. For a globally installed CloudCLI those are two different trees: the install lands in whatever directory the user happened to launch the CLI from (often the home directory), which node never walks into when resolving from `<npm root -g>/@cloudcli-ai/cloudcli/dist-server/server/modules/browser-use/`. So the install genuinely succeeds, the Settings tab still reports `Playwright: missing`, and the "Install Runtime" button looks like it does nothing no matter how often it is clicked — each click just reinstalls into the same unreachable place. Installing now targets `~/.cloudcli/browser-use/runtime` (beside the existing `profiles/` dir), seeded with a private `package.json` so npm does not walk up and adopt whatever project sits above it, and `getPlaywright()` tries the module's own resolution first and that directory second. `runCommand()` took a `cwd` argument for this. Dropping `--no-save --no-package-lock` is safe now that the manifest is fork-owned, and keeping the lockfile makes reinstalls cheaper.

**On upstream conflict:** This is a plain bug fix rather than a fork preference. **Already reported upstream by others** — [#995](https://github.com/siteboon/claudecodeui/pull/995) proposes an identical fix (same `~/.cloudcli/browser-use/runtime` directory, same resolve-order), with [#1000](https://github.com/siteboon/claudecodeui/pull/1000) and [#917](https://github.com/siteboon/claudecodeui/pull/917) covering the same root cause; all three open and unanswered since June–July 2026. Don't file a fourth (see `docs/pull-requests/PR04-browser-runtime-install-directory.md`). If any of them merges, take upstream's version and retire this entry. Until then keep mine, but treat `installRuntime()` and `getPlaywright()` as a pair: they only work together, so if upstream rewrites either one, reapply both halves rather than merging one side and leaving the other. If upstream instead solves it by shipping playwright as a real dependency, drop this entirely — the first resolver already covers that case.

## 15. Tab switcher collapses into a menu on mobile

**Files:** `src/modules/project-workspace/MainContentTabMenu.tsx`, `WorkspaceTabs.tsx` (formerly `MainContentTabSwitcher.tsx`), `WorkspaceHeader.tsx` (formerly `MainContentHeader.tsx`), `src/shared/ui/ActionMenu.tsx`

**Why:** Upstream puts the header title and the tab pills on one row. Below `lg:` the pills are already icon-only, but the count is not fixed — 4 built-ins plus optional Browser and Tasks plus one per enabled plugin — so on a 375px phone the strip takes ~148–220px and the title is left with under 150px (measured 51px with 6 tabs). Upstream's own mitigation, a horizontal scroller with gradient fade masks, stops the overflow but hands the title no width back. That costs more in this fork than upstream because entry 13 turned the chat title into the cross-project session switcher, so squeezing it also squeezes a navigation entry point. Below 768px — `isMobile`, the same flag the header already uses for the hamburger — the whole strip now collapses into one ~48px pill showing the active tab's icon plus a chevron; tapping it opens a dropdown listing every tab in the current order, divider before the plugin group, active row highlighted and marked `aria-current`. ## 16. Push notifications collapse to one-per-session, cleared on open or once resolved elsewhere

**Files:** `server/modules/notifications/services/notification-orchestrator.service.js`, `server/modules/notifications/index.ts`, `server/modules/providers/list/claude/claude-runtime.provider.js`, `public/sw.js`, `src/modules/project-workspace/hooks/useClearSessionNotifications.ts` (new), `src/modules/project-workspace/ProjectWorkspaceRoute.tsx`

## 20. Scheduled session triggers (send a message later) ❌ retired (v1.37.3)

**Files:** `server/modules/database/schema.ts`, `server/modules/database/index.ts`, `server/modules/database/migrations.ts`, `server/modules/database/repositories/scheduled-triggers.db.ts`, `server/modules/database/repositories/sessions.db.ts` (+ test `server/modules/database/tests/sessions.db.integration.test.ts`), `server/modules/scheduled-triggers/` (new module: `index.ts`, `scheduled-triggers.routes.ts`, `services/scheduled-trigger.service.ts`, `services/scheduler-poller.service.ts`, `tests/`), `server/index.ts`, `server/modules/notifications/services/notification-orchestrator.service.js`, `server/modules/websocket/services/chat-websocket.service.ts`, `.env.example`, `src/shared/api.ts`, `src/modules/chat/hooks/useScheduledTrigger.ts`, `src/modules/chat/composer/ComposerScheduleMenu.tsx`, `ChatComposer.tsx`, `src/modules/chat/ChatInterface.tsx`, `src/modules/i18n/locales/en/chat.json`

**Why:** Some Codex/Claude relays (third-party API resellers) enforce their own rate-limit windows and return a plain-text error naming a clock time to retry after (e.g. `请在 今天 15:00 后再试`) instead of a structured `retry-after`. Upstream has no notion of "wait, then resend" at all — a rate-limited session just sits there until the user manually comes back and retypes. This adds a generic, provider-agnostic "schedule a message" primitive: any session can queue a one-shot future message (defaulting to `continue`, editable) via a new clock-icon composer menu; a 30s backend poller fires it through the same `providerRuntimeService.run()` seam `chat.send` and the headless `/api/agent` route already share, so no provider gets special-cased.

The poller claims a trigger (`pending` → `firing`) *before* calling the provider, not after — the first version marked it fired only on success, so a provider call slower than one poll interval got re-picked-up and fired again by the next tick (observed firsthand: a slow response sent the same `"continue"` into a live session repeatedly). A trigger stuck `firing` from a crash mid-fire is reset to `pending` on the next boot so it isn't lost forever, just retried.

The composer UI is time-only — no date picker at all. A bare `HH:mm` always means "the next occurrence of that clock time": today if it hasn't passed yet, tomorrow (at most 24h out) otherwise — computed fresh on every render, not decided once and stored. An earlier version *did* store that decision on the input's `onChange`, and a native time input fires `onChange` once per segment as you type (hour, then minute) rather than once when you're done; a not-yet-finished intermediate value could permanently latch onto "tomorrow" mid-edit even though the value you finished typing was still later today. A plain, non-interactive "Tomorrow" label appears next to the input when applicable; there's deliberately no way to pick an arbitrary date. Five presets cover the common cases: `+10min`/`+60min` (stack — each click adds to whatever's currently drafted, not to "now"), the next on-the-hour mark, the next `{0,3,6,9,12,15,18,21}` mark, and a fixed `00:05` "first thing tomorrow" shortcut. Reopening the popover always resets to a fresh default rather than whatever was left over from a previous open/schedule/cancel.

Deliberately scoped to a manual, one-shot primitive for this pass — automatically detecting a relay's rate-limit text and auto-creating a trigger from it is an intentionally deferred follow-up, not built here. Fires headlessly (no live WebSocket client attached), so an already-open chat tab does not see the reply stream in — it only learns the session changed via a `session_upserted` ping, which the frontend already treats as sidebar-only; genuinely live-streaming a headless-fired run into an open tab is unaddressed. Missed triggers (server down at `trigger_at`) fire late within a configurable grace window (`SCHEDULED_TRIGGER_GRACE_WINDOW_MINUTES`, default 60) and are marked `expired` beyond it, rather than either silently dropping or firing an arbitrarily stale message.

A scheduled run must behave like the user typing the command — permission included. As first shipped, a trigger fired with an empty allowlist and the provider's *default* permission mode (the session's own mode lived only in browser localStorage), and the headless writer's no-op `send` dropped the `permission_request` frame, so a tool the user's interactive mode would have approved hit the wall silently: ordinary tools auto-denied after 55s, the trigger was still marked `sent`, and the user saw an incomplete result. The fix records the resolved `permissionMode` the client already sends in every `chat.send` onto a new nullable `sessions.permission_mode` column (same pattern as the per-send `model`/`effort` recording, zero frontend change), the fire path passes the stored value through the existing `permissionMode` runtime option — nothing passed when unset, so the provider default applies — and the headless writer relays `permission_request`/`permission_cancelled` frames to every connected client (remapped to the app session id, since the runtime labels them with the provider-native id) instead of dropping all frames. Everything downstream of the frame is untouched and writer-independent — the 55s/unbounded timeouts, the `permission.required` push, the `chat_subscribed.pendingPermissions` catch-up, and the `chat.permission-response` resolution — so a scheduled prompt is answerable from any device exactly as an interactive one. The tool allowlist is deliberately *not* persisted or inherited: it is a global browser setting rather than a per-session one, and redundant for completion now that the prompt actually reaches the user. Documented hard limit, not a defect: "consistent with the client" does not mean "completes unattended" — with no device present a prompt auto-denies after 55s, exactly like a typed prompt left alone; unattended jobs set the session to `bypassPermissions`, which the trigger then inherits. See `docs/adr/0010-scheduled-triggers-inherit-the-session-permission-mode.md`, now marked superseded for the same reason this entry is retired.

**Retired (v1.37.3):** v1.37.3 brought upstream's own scheduling feature (`scheduled_messages` table + `server/modules/scheduled-messages/`), and carrying both meant two schedulers, two tables and two composer entry points for one promise. Upstream's is the deeper one — it runs a scheduled message as a full `chatRunRegistry` turn through `runDetachedChatTurn`, so the run is subscribable, replayable and marks the session busy everywhere, where the fork's fired headlessly and only pinged `session_upserted` — so the fork's surface was removed whole rather than adapted onto it. Deleted: `server/modules/scheduled-triggers/` (routes, service, poller, tests), `server/modules/database/repositories/scheduled-triggers.db.ts`, the `scheduled_triggers` table and its indexes in `schema.ts`/`migrations.ts`, `src/modules/chat/hooks/useScheduledTrigger.ts`, `src/modules/chat/composer/ComposerScheduleMenu.tsx` and its slot in `ChatComposer.tsx`, the `src/shared/api.ts` methods, the `en/chat.json` keys, and the boot/route wiring in `server/index.ts`.

**What was given up with it, deliberately:** ADR 0010's two additions do not exist in upstream's design and were not ported. Upstream snapshots the composer's options (model, effort, permission mode, attachments) as JSON *at schedule time*, so a scheduled run carries the mode the composer happened to hold when the message was drafted rather than the session's mode at fire time; and upstream's dispatcher does not relay `permission_request`/`permission_cancelled` frames out of a run nobody is watching, so a scheduled run that hits a permission wall still auto-denies after 55s with no prompt reaching a device. That is a real regression against the fork's own version and was accepted as the price of one scheduler; reporting it upstream is tracked separately. Two leftovers are load-bearing to know about: the nullable `sessions.permission_mode` column, its `addSessionPermissionModeColumn` migration and `sessionsDb.setSessionPermissionMode` all survive, and `chat-websocket.service.ts` still records the mode on every `chat.send` — but **nothing reads it any more**. Don't delete it on sight (dropping a column needs a migration of its own) and don't assume it is wired to anything.

**Historical — the fork's own conflict guidance, kept for the record:** New table + new module, near-zero conflict surface on its own; the only edits to files upstream also owns were additive (one `CREATE TABLE IF NOT EXISTS` block + two indexes appended to `INIT_SCHEMA_SQL` in `schema.ts`, one nullable `permission_mode` column in `SESSIONS_TABLE_SCHEMA_SQL` plus one `addSessionPermissionModeColumn` step in `migrations.ts`, one `setSessionPermissionMode` method + row field in `sessions.db.ts`, one repository export line in `database/index.ts`, two route-mount/poller-start lines plus one import in `server/index.ts`, one `ComposerScheduleMenu` slot in `ChatComposer.tsx` next to the existing `ComposerPermissionMenu`, one `sessionId` prop threaded from `ChatInterface.tsx`, two new `CODE_MAP` entries in the notification orchestrator, and ~3 lines of `permissionMode` recording next to the existing model/effort recording in `chat-websocket.service.ts`). If upstream touches `chat-websocket.service.ts`'s `runtimeOptions` construction (`cwd`/`projectPath` from the session row) or the model/effort recording block, mirror the same shape in `scheduled-trigger.service.ts`'s `fireTrigger()` and re-apply the `permissionMode` recording — they were deliberately copied from there rather than factored into a shared helper. Upstream has since grown its *own* scheduling feature (`scheduled_messages` table + `server/modules/scheduled-messages/`) with a different design: it snapshots the composer options (model, effort, permission mode, attachments) as JSON *at schedule time* and runs them as full `chatRunRegistry` turns via `runDetachedChatTurn` (subscribable/replayable, busy everywhere), whereas the fork's triggers inherited the session's last-sent mode *at fire time* and kept the headless + `session_upserted`-only ping. The token-usage panel's Compact button lives in `CommandResultModal.tsx`'s modal footer, next to Close, so it stays reachable and tappable regardless of the panel's content height on small screens; it calls a new `triggerCompact` in `useChatComposerState.ts` that writes `/compact` into the input and submits it through the same write-back-then-submit mechanism `handleCustomCommand` already uses for custom commands — never the backend command endpoint, which has no `/compact` handler to route to. `useChatProviderState.ts`'s own frontend capability mirror deliberately has **no** per-provider fallback guess for `supportsCompact`, unlike `supportsEffort`'s guessed fallback: before `/api/providers/capabilities` resolves, or if that request fails, every provider reads as unsupported, so the entry stays hidden rather than briefly appearing for a provider that cannot run it.

Issue [#21](https://github.com/wltiger/my-cloudcli/issues/21) lands OpenCode's side of `supportsCompact`. OpenCode has no equivalent to the SDK's inline compaction: `opencode run`'s positional message is plain text with no slash-command expansion (verified against 1.18.18), so `/compact` can never reach the model as a prompt, and the only endpoint that performs compaction lives on OpenCode's HTTP server, not the one-shot CLI. The fork lives entirely inside `spawnOpenCode` in `opencode-runtime.provider.js`, as a single early return before its existing `return new Promise(...)`: when the raw command is exactly `/compact`, `runOpenCodeCompactSideChannel` starts a short-lived headless `opencode serve --port 0 --hostname 127.0.0.1` (OpenCode's session storage is global, so any server instance can address any session — confirmed in #18 by starting a server in an unrelated directory and having it list sessions belonging to other projects), waits for the server's own stdout to confirm it is listening (that line is only printed once the socket is already accepting connections, so no separate readiness poll is needed), then POSTs to the legacy unprefixed `/session/{id}/summarize` with a `{providerID, modelID}` body split from the same `resolveResumeModel` result the one-shot path already resolves for its `--model` flag — deliberately not a second model lookup. The server is always shut down: `startOpenCodeServeProcess` kills its own process before rejecting if the server never becomes reachable (spawn error, early exit, or a 15s startup timeout), and the caller's `finally` kills it once reachable, regardless of whether the POST that follows succeeds, fails, or throws. The one-shot `opencode run` path underneath is untouched by any of this.

This is also where the two endpoints named in #18's original research turned out to be wrong, measured by hand against a real 1.18.18 session (see [#21](https://github.com/wltiger/my-cloudcli/issues/21)'s comments) and now encoded directly in the runtime: `POST /api/session/{id}/compact` — the endpoint #18 originally documented from OpenCode's own OpenAPI schema — is declared but not implemented in 1.18.18; it answers `503 {"message":"Session compact is not available yet"}`. The endpoint that actually works is unprefixed: `POST /session/{id}/summarize`. Worse, the prefixed guess at the working route, `/api/session/{id}/summarize`, is not a route at all — it falls through to the web UI's HTML catch-all and answers `200` with an HTML body, an easy false positive if only the status code is checked. `runOpenCodeCompactSideChannel` always parses the response body and requires it to be the JSON literal `true`; a non-2xx status or an unparseable/non-`true` body are both treated as failure, so that HTML catch-all fails loudly instead of reading as a silent success.

`opencode-sessions.provider.ts` gets one more part-type branch, `compaction`, appended after the existing `text`/`reasoning`/`tool`/`patch`/`agent` dispatch in `normalizeHistoryRows`. OpenCode persists a compaction as a `{type: "compaction", auto: boolean}` part — no token counts, unlike Claude's SDK event — on its own synthetic user-role message with no accompanying text part; the summary that follows arrives as an ordinary assistant text message immediately after, needing no special handling (the OpenCode analogue of Claude's `isCompactSummary` flag, but here the existing `text` branch already renders it correctly as-is). Because the dispatch is per part rather than per message, that empty-text user message never also hits the `text` branch above it, so the empty-user-bubble gotcha needed no extra guard code — the existing per-part loop structure already keeps it out. `auto` maps onto the same `compactTrigger` field #19 introduced (`false` → `manual`, the only value observed from the side channel; `true` → `auto`, for whenever OpenCode compacts on its own, unobserved so far). `compactPreTokens`/`compactPostTokens` stay undefined, which #19's renderer already handles by showing the trigger only.

**Why:** From any message in a Claude chat the reader can take a **Fork** — see `CONTEXT.md`'s glossary for that term, and for **Anchor**, **Transcript row** and **Compact**, which this entry leans on throughout. The conversation up to that point is copied into a new session with its own id; the original is left untouched and still resumable. Upstream has no concept of this. Ticket [#22](https://github.com/wltiger/my-cloudcli/issues/22); this is the tracer bullet for a five-ticket set ([#23](https://github.com/wltiger/my-cloudcli/issues/23) OpenCode fork, [#24](https://github.com/wltiger/my-cloudcli/issues/24) Clear, [#25](https://github.com/wltiger/my-cloudcli/issues/25) Claude rewind, [#26](https://github.com/wltiger/my-cloudcli/issues/26) OpenCode rewind), so most of what landed here is the seam those tickets attach to rather than the button itself.

The load-bearing decision is that **an Anchor is computed on the backend and shipped with each message**, as a new optional `anchor` field on `NormalizedMessage`. It cannot be derived on the frontend: `normalizeMessage` mints composite ids (`${baseId}_tr_${tool_use_id}`, `${baseId}_text_${partIndex}`, `${baseId}_text`, `${baseId}_images`), so what the frontend holds is never a clean transcript uuid — and one rendered message is not one transcript row anyway. `claude-anchors.ts` — a fork-owned pure function, `buildClaudeAnchorIndex(rows)` — takes the raw JSONL rows and returns row-uuid → anchor-uuid, and `fetchHistory` stamps each normalized message with the anchor of the row it came from. Three measured facts shape it, all confirmed against real transcripts and SDK 0.3.165 rather than read from docs: (1) one agent turn is written as several rows — reasoning, text, one per tool call — sharing the same `message.id`, and `forkSession`'s `upToMessageId` is **inclusive**, so a turn's anchor is its **last** row; anchoring at the first row silently truncates the turn. (2) Those rows are **not necessarily adjacent**: an assistant message issuing two tool calls has each tool result written between its two `tool_use` rows, so the grouping is by `message.id` across the whole transcript, not by consecutive run — a run-based grouping passes the simple case and quietly splits the parallel-tool case. (3) Every row up to and including the **last compaction boundary** gets no anchor at all, so the frontend offers no entry there: a Rewind anchor from before a Compact is known to fail hard (`resumeSessionAt` → `No message found with message.uuid of: …`), Fork's tolerance was never measured, and the conservative rule applies to both. Observed live on a session with two `/compact` runs: every message at or before the boundary came back with no anchor, the one after it carried one.

Fork itself is a **pure file operation** — the SDK copies the transcript, remaps every uuid, preserves the parent chain, writes `<newSessionId>.jsonl` next to the original in the same project directory, and neither runs the model nor costs tokens. `dir` is the *workspace* path, the same value the session row stores as `project_path`, not the `~/.claude/projects/...` folder. Because uuids are remapped, the fork's own anchors are recomputed from its own file and differ from the source's — which is exactly why an anchor is never persisted anywhere.

The provider seam is one **optional** method, `forkSession?`, appended to `IProviderSessions`, deliberately rather than a per-provider `if` inside the service: providers disagree about whether the anchored row is kept or dropped (OpenCode's fork excludes it while its own revert includes it), so each implementation owns that, and #23/#26 add theirs the same way. `session-fork.service.ts` owns everything provider-independent: it resolves the provider through `providerRegistry`, calls the facet, then registers the copy. Registration is three `sessionsDb` calls and each is load-bearing — `createAppSession` (app-allocated id + the fork's name), `assignProviderSessionId` (records the mapping, merging the row the watcher may already have created), then `createSession(...)` purely to write `jsonl_path`, which is exactly what the sessions watcher would do on its next pass and which the fork needs *now* or it opens looking empty. The app-session shape (`session_id` ≠ `provider_session_id`) is not cosmetic: `createSession`'s `custom_name` CASE only preserves a name when those two differ, so registering the fork under its provider id instead would let the next synchronizer pass overwrite `[Fork] …` with a title derived from the first user prompt. Model and reasoning effort are copied from the source row so the fork resumes with the same runtime configuration.

The naming dialog is pre-filled with `[Fork] <original name>`, sequence-numbered (`(2)`, `(3)`, gaps filled) when that name is already taken in the same project, archived sessions included. That suggestion is resolved on the **backend** (`GET /sessions/:sessionId/fork-name`) because the frontend's project payloads are paginated and only hold the first page of names, so it cannot tell what is taken; the hook fetches it *before* opening the dialog, so the input is never briefly empty or briefly wrong. `buildForkSessionName` is exported purely so the naming rule is pinned by tests. Nothing is created until confirm — verified: cancelling left zero rows and zero new transcript files.

On the frontend, `supportsFork` follows the `supportsCompact` precedent from entry 22 exactly, including its **no-fallback** rule: `getSupportsForkForProvider` reads false for every provider until `/api/providers/capabilities` resolves, so the entry stays hidden rather than briefly appearing for a provider that cannot fork. There is no per-provider branching anywhere in `src/` — a message either carries an `anchor` or it does not. `anchor` rides through `useChatMessages.ts`'s `sharedMetadata`, the one object spread into every emitted message kind, rather than through a per-kind `case`, because it applies to all of them. The entry is also hidden while a run is in flight (`!isProcessing`), which happens to cover the one real gap: **live-streamed messages carry no anchor**, because a turn's anchor is not knowable until that turn's last row exists. This self-heals rather than needing code — the sessions watcher sees the transcript change, the chat pane reloads history, and the finished turn gains its anchor; observed directly by sending a message into a fork and watching the new turn become forkable seconds later. Confirming a fork switches the UI through `handleSessionEstablished`, the same handoff a brand-new session uses, so the sidebar picks it up without a second parallel path; the fork is renamed afterwards through the sidebar's existing inline rename, and no second rename was built.

A **prefactor** shipped with this and is worth knowing on its own: `claude-sessions.provider.ts` had a module-local `async function getSessionMessages(...)` whose name collides with the SDK's own `getSessionMessages` export that #25 needs to import into this same file (see ADR 0007). It is renamed to `readClaudeTranscriptRows`, which also just describes it better.

Issue [#23](https://github.com/wltiger/my-cloudcli/issues/23) lands OpenCode's side of `supportsFork`, and it is the ticket that justifies the whole opaque-anchor design. `opencode-anchors.ts` is a **second, parallel** fork-owned pure function, `buildOpenCodeAnchorIndex(rows)` — deliberately not a generalization of Claude's, because the two rules disagree. Measured against a real 1.18.18 session: `POST /session/{id}/fork {messageID}` is **exclusive**, producing a session that ends *before* the message it is given (forking at the message that closed a turn dropped that turn's reply). OpenCode splits a turn across several messages just as Claude does — a turn that wrote a file came back as two assistant messages, one carrying the tool call and one the reply text — so "the anchor is the end of the turn" still holds, but exclusivity moves it one row further on: **a turn's anchor is the first message of the *next* turn**, where Claude's is the turn's own last row. A turn here is a user prompt on its own, or a run of consecutive assistant messages; anchoring on the next *message* rather than the next *turn* passes the single-message case and silently truncates the tool-using one. OpenCode's own `revert` (#26) then disagrees again by *including* the message it is given — same provider, opposite conventions — which is exactly why an anchor is an opaque per-provider token and must never be folded into one shared rule.

The newest turn has nothing after it to name, so it gets `OPENCODE_SESSION_END_ANCHOR`, a sentinel that module exports: measured, `POST .../fork` with **no** `messageID` at all copies the session whole, which is precisely "ends at the last turn". Without it the entry would vanish on exactly the messages a reader forks from most. Anchors are stamped inside `normalizeHistoryRows` through a one-line `push` closure rather than at each of its seven emit sites, and messages at or before the last compaction get none — the same conservative rule Claude's index applies, and the reason the `compaction` part-type branch entry 22 added is read a second time here.

Reaching the endpoint reuses the **same** short-lived headless `opencode serve` Compact ([#21](https://github.com/wltiger/my-cloudcli/issues/21)) already starts, rather than adding a second one: `forkOpenCodeSession` lives in the fork-owned `opencode-serve.ts` and borrows the runtime provider's own `startOpenCodeServeProcess`/`killOpenCodeProcessTree` through `withOpenCodeServe` — the single start/use/shut-down bracket, which kills the server on success, failure and throw alike, and which all four callers (Compact, fork, revert, unrevert) now go through. `opencode-sessions.provider.ts`'s `forkSession` facet method is that one call and nothing else — the sessions facet importing `opencode-serve.ts` is deliberate, and is what keeps the headless server a single implementation. The OpenAPI-is-wrong lesson from #21 applies verbatim and was re-measured here: `/api/session/{id}/fork` is not a route, falls through to the web UI's HTML catch-all and answers `200` with an HTML body, so a fork counts only when a session id is read *out of the body* of the legacy unprefixed `/session/{id}/fork`. Finally, that endpoint **takes no title** — OpenCode names the copy `<original> (fork #1)` — so the `[Fork]` name is applied afterwards as a separate `PATCH /session/{id}` with `{title}`, confirmed by reading the title back out of the response; a rename that does not stick warns rather than losing the fork, since CloudCLI shows its own name for it either way. Verified end to end against a real session: forking mid-conversation produced a copy ending at the chosen message's *whole* turn (tool call and reply text both kept, nothing from the turn after), forking the newest message copied all of it, both copies carried `[Fork] …` in OpenCode's own session list, and the original still had every message and still resumed.

Issue [#24](https://github.com/wltiger/my-cloudcli/issues/24) adds **Clear** — again see `CONTEXT.md` for the term. It is the one operation in this set that reaches **no provider API at all**, which is why both Claude and OpenCode got it in a single ticket and why it contains no per-provider code anywhere. ADR 0005 is the decision and it supersedes ADR 0003, which had planned Clear as a Rewind to zero: measured on Claude, `resumeSessionAt` fails hard on any uuid it cannot resolve (`No message found with message.uuid of: …`) and the first user message carries `parentUuid: null`, so there is no row before it to anchor on — Clear cannot be expressed as a Rewind. OpenCode *can* empty a session in place (`POST /session/{id}/revert` against the first message, even undoably through `/unrevert`) and that was deliberately **not** used: one button that adds a sidebar entry on one provider but not the other is worse than a uniform one.

`session-clear.service.ts` is the whole backend — it renames the open session to `[Cleared] <name>`, archives it, and allocates an empty app session in the same project. Three details carry the design:

- The prefix is a **fixed English literal written into `custom_name`**, not a translated string and not a rendered badge, so it survives a language switch and the sidebar's existing inline rename can edit it afterwards. `buildClearedSessionName` is exported only so the rule is pinned by tests, and clearing an already cleared session **nests** (`[Cleared] [Cleared] …`) exactly as `buildForkSessionName` does rather than collapsing the prefix.
- The archive is durable **only because the retired row is never written again**. `createSession`'s upsert sets `isArchived = 0` on every write and the synchronizer is incremental, so an untouched retired session stays archived and **un-archives by itself** the moment the reader resumes it. That self-healing is the feature; there is deliberately no special case keeping it archived. Verified on both providers: resuming a retired conversation put it back in the active list within seconds, through the ordinary sessions-watcher upsert and nothing else. Measured caveat: a retired session that was **provider-shaped** to begin with loses its `[Cleared]` prefix at that same moment, because the upsert's `custom_name` CASE only preserves a name while `session_id` ≠ `provider_session_id`. The marker and the archive fall away together, which reads correctly — but it does mean the prefix survives a resume only on app-shaped sessions.
- The empty session is created with **no name at all** — `sessionsDb.createAppSession` without `customName` — which is the mirror image of the trap #22 hit. It needs the app-session shape (`session_id` ≠ `provider_session_id`) *and* a NULL `custom_name`, because the upsert's `custom_name` CASE only lets a synchronized title land while the name is still NULL; routing it through the session gateway's `buildCloudCliSessionName('')` instead would have frozen the new session at "Untitled Session" forever. Model and reasoning effort are copied from the retired session, so the reader carries on with the runtime configuration they were already working in.

`supportsClear` follows the `supportsCompact`/`supportsFork` precedent exactly, no-fallback rule included. Because no runtime is involved, the flag records where Clear was **verified** rather than what a provider can do: Claude and OpenCode true, Codex and Cursor simply unverified. The service refuses a provider whose flag is false, so the capability is not merely decorative.

On the frontend Clear is a **composer command-menu entry** — not a sidebar action and not a per-message control. `clearCommand.ts` mirrors `compactCommand.ts` but is deliberately a second function rather than a generalization of it, because the two disagree about what picking them means: Compact must reach the provider verbatim, Clear must never leave CloudCLI. Both ways in — picking it from the menu, and typing `/clear` and sending — funnel through `executeCommand`, so one clause at the top of that function covers both and keeps `/clear` away from `/api/commands/execute`; verified live that a typed `/clear` retires the conversation with no command-execution error. A project command that already owns the name wins: the entry is skipped rather than replacing it.

The one real surprise is in the **sidebar**, not the backend. Archiving alone does not remove the retired conversation from the active list: `/api/projects` correctly stops returning it, but `mergeExpandedSessionPages` re-adds any session the client had already loaded whenever the incoming payload holds fewer sessions than the previous state — a pagination guard that also protects a session which legitimately left. A refetch therefore cannot fix it, and was observed doing exactly the wrong thing. The retired id instead rides along on the existing `SessionEstablishedContext` as `retiredSessionId`, so `registerOptimisticSession` drops it in the **same** `setProjects` call that inserts the session replacing it — atomic, so the two can never both be listed even for a frame, and no new prop threading.

Left alone on purpose: an empty session's `GET …/token-usage` answers 404 because it has no provider session yet, and the browser console logs it. The frontend already treats a non-ok response as "no token budget", so nothing user-visible happens; Clear is simply the first path that opens a session id before any run exists.

Issue [#25](https://github.com/wltiger/my-cloudcli/issues/25) adds **Rewind** on Claude — again see `CONTEXT.md`. Two decisions shape all of it. ADR 0006 is the first: `resumeSessionAt` is an option on the *next query*, not an operation, so there is deliberately **no "rewound but not sent" state**. Choosing Rewind only loads the message back into the composer, dims it and everything after it, and shows a notice; **pressing send is what performs the Rewind**, and a reload cancels one that was never sent. A persisted pending-anchor was considered and rejected — do not add one back.

The Anchor rule is a **second, concrete rule** beside Fork's, deliberately not a generalization of it — same provider, same gesture shape, different row. `forkSession` is inclusive of a turn's **last** row; `resumeSessionAt` is inclusive of the row it **names**, so rewinding *to* a message means anchoring on the row **before** it. `claude-rewind.ts`'s `buildClaudeRewindAnchorIndex(rows)` reads that row off the `parentUuid` chain rather than off file order, because a turn's rows are interleaved with tool results. Three measured facts decide the walk: (1) only **user** rows get an anchor, because Rewind is offered on the reader's own messages only — unlike Fork, which is offered on both. (2) The walk climbs past rows the SDK's own reader would not return: measured across every local transcript, 19 of 591 user prompts have an `attachment` row as their direct chain parent (a pasted image or dropped file is written as its own row immediately before the prompt it belongs to) and one has a `system` row — anchoring on either hands `resumeSessionAt` a uuid it cannot find. (3) Nothing at or before the last compaction boundary gets one, which also covers the first prompt after a boundary (its whole chain lies above it) and the very first prompt of a session (no row before it at all) — the same fact that made Clear impossible to express as a Rewind (ADR 0005).

The second decision is ADR 0007, and it is why **branch filtering ships in this ticket** rather than a later one. A Rewind does **not** rewrite the transcript — it turns it into a tree. Verified directly on a rewound session: the new turn is appended to the same file with its `parentUuid` pointing back at the anchor, both branches stay physically present, and CloudCLI's flat reader keeps rendering the abandoned one, so without filtering the feature has a visible "the old messages came back" bug on **every** reload. The SDK has a branch-aware reader, `getSessionMessages` — note it returns a plain `Promise<SessionMessage[]>`, **not** an async iterable — but it also discards everything before a compaction boundary, which would take the boundary marker (this same entry's #19 slice) and all the history above it off the screen. So `filterClaudeAbandonedBranchRows(rows, activeRowUuids)` applies the filter **only after the last boundary**; everything before it renders flat exactly as it did. That is safe precisely because an anchor from before a Compact cannot resolve at all, so no abandoned branch can exist there.

The filter's load-bearing subtlety is **which rows it is allowed to drop at all**. `getSessionMessages` returns only `user`/`assistant` rows and drops meta, sidechain and every other type (`attachment`, `ai-title`, `last-prompt`, `queue-operation`, `mode`, `system`). Their absence from the active set therefore says nothing about which branch they are on, so a row is eligible to be dropped only if the SDK would have returned it — treating a plain "not in the set" as abandoned would silently delete the reader's attachments and subagent output. An **empty** set means the branch could not be read and filters nothing, because losing the whole conversation is far worse than an abandoned branch staying visible. One measured near-miss worth keeping: parallel-tool turns make an ordinary, never-rewound transcript genuinely branch — an assistant message issuing two tool calls has each tool result written between its two `tool_use` rows, so 68 of 102 local sessions have rows sharing a `parentUuid`. `getSessionMessages` resolves every one of them with **zero** loss (checked row by row), which is what makes the filter safe; a hand-rolled single-chain walk would have quietly halved those turns.

Swept across all 103 local transcripts the filter changes **nothing** in 94 of them. In the 9 that change, the dropped rows are genuinely off the active chain: explicit abandoned branches, and dead-end assistant rows (a failed "API Error" turn; a turn superseded by a `system` row taking over the chain from the same parent). Worth knowing as a **visible behaviour change** rather than a no-op: sessions rewound outside CloudCLI — Claude Code's own CLI does the same thing — now render without their abandoned branches too, where before they showed both.

On the frontend `supportsRewind` follows the `supportsCompact`/`supportsFork`/`supportsClear` precedent exactly, no-fallback rule included, and is deliberately **separate from `supportsFork`**: OpenCode can fork today but cannot rewind until #26, so one shared flag would offer an entry that does nothing. `NormalizedMessage` gains a second optional field, `rewindAnchor`, rather than overloading `anchor` — two operations, two rows, both opaque to the frontend, which still holds zero per-provider rule. The composer work is split across two hooks in one fork-owned file purely for **hook ordering**: `useSessionRewind` must run *before* `useChatComposerState` so its Anchor can ride along with the send, while `useRewindComposerPrefill` must run *after* it because the setters it writes through only exist then. Attachments come back with the text — Claude persists a user turn's images inline as base64, so the common case needs no network at all (`fetch` reads a data URL directly), and stored non-image files fall back to the asset store. Verified with a real image: two attachments restored byte for byte (85 and 98 bytes, correct MIME, the valid one rendering 32×32 in the composer chip).

**Backing out puts the composer back exactly as it was.** Starting a Rewind is destructive — it overwrites whatever the reader was typing, attachments included — so `useRewindComposerPrefill` saves the composer's contents at the moment the draft is applied and hands them back on cancel. Without that, a reader half-way through a message who opens a Rewind to check what they had said and then presses Esc loses their own draft with no undo; that is a real loss path, not a cosmetic one, and it contradicts the ticket's own "Esc backs out and restores the view with nothing changed". Two details make it work. The save is read **inside the effect that applies the draft**, because on that render the composer still holds the reader's text; the live values reach that effect through a ref synced by its own effect, so the apply does not re-run on every keystroke. And **only cancel restores** — sending also makes the draft disappear, but the send has already emptied the composer and restoring there would refill it. That is why `useSessionRewind` exposes a plain `clearRewind` (used by the send path and by the session-switch reset) while the restoring `cancelRewind` is **returned by `useRewindComposerPrefill`** and wired only to the notice's Esc/✕. Do not collapse the two into one function; the wrong one on the notice silently reintroduces the draft loss, and the wrong one on the send refills a composer that was just emptied. Nothing is persisted, so a reload still cancels a never-sent Rewind without restoring anything (ADR 0006). The same save/restore closed a second bug on the way: applying a draft now calls `setAttachedFiles(files)` **unconditionally** rather than only when non-empty, so rewinding to a message that had no attachments drops whatever the composer was holding instead of letting it ride along into the send.

One behaviour is deliberate and worth not "fixing" by accident. **The entry is hidden while a run is in flight** (`!isProcessing`), which also covers the one real gap it shares with Fork: live-streamed messages carry no anchor, because a turn's anchor is not knowable until its transcript row exists. Like Fork's, this self-heals through the sessions watcher rather than needing code. Rewind is a **per-message control, not a slash command**, so it deliberately goes nowhere near `executeCommand`'s interception clause or the skill/compact pass-through exemption.

Verified live end to end on a real Claude session: a three-turn conversation rewound at its middle message continued under the **same session id**, the abandoned turns left the stream, and — the crux — were **still gone after a reload**, while the transcript on disk still physically held them under a parent with two children. A separate session with two `/compact` runs still rendered its pre-boundary history and its `Compacted · 47,256 → 3,272 tokens` marker, and offered **zero** Rewind entries anywhere in it. The entry appeared on 2 of 3 user messages (the first has no row before it), on none of the assistant messages, and dropped to 0 for the duration of a run.

Issue [#26](https://github.com/wltiger/my-cloudcli/issues/26) finishes the set with **Rewind on OpenCode**, and it is the one place in it where a gesture touches the reader's code. OpenCode has no `resumeSessionAt`; it has `POST /session/{id}/revert`, which rolls the session back **and restores tracked files to their state at that point** — measured, a tracked file went from `hello v3` back to `hello v2` the moment the call returned. Whether a Rewind touches files is settled by the provider rather than offered as a choice (the Rewind entry in `CONTEXT.md`), so there is no toggle: the capability matrix gained a second flag, `rewindRestoresFiles`, whose only job is to let the notice above the composer say so **before** the reader commits. That extra line is the *entire* frontend change — everything else (the entry, the dimming, the prefill, Esc, cancel-restores-the-composer) was already provider-agnostic and needed nothing.

The Anchor rule is a **third** concrete rule, and it disagrees with the other two on the same provider. `opencode-rewind.ts`'s `buildOpenCodeRewindAnchorIndex(rows)` maps a user message to **itself**, because revert is *inclusive* — naming a message drops that message and everything after it. Its own fork is *exclusive*, so `buildOpenCodeAnchorIndex` maps that same message to the first message of the **next** turn, a row further along. Same provider, same gesture shape, opposite conventions; this is the concrete case that justifies an Anchor being an opaque per-provider token, and the three rules must stay separately readable rather than being folded into one. Two smaller differences from Claude's rule are deliberate: only user messages get one (as on Claude), but **the first prompt of a session does get one here** — Claude's rule anchors on the row *before* a message and the first prompt has none, whereas revert names the message itself, so rewinding the opening prompt legitimately means "empty the session and roll every file back". And nothing at or before the last compaction gets one, the same conservative rule the fork index applies, which is load-bearing twice over: the filter below refuses to touch that segment, so an anchor there would revert server-side and still render everything it reverted. `opencode-anchors.ts` now exports `readOpenCodeMessageIndex` (plus the row/summary types) — one scan that collapses per-part rows back into messages and finds the last compaction — consumed by all three rules, exactly as `claude-anchors.ts` exports `findLastCompactBoundaryIndex` to `claude-rewind.ts`. `buildOpenCodeAnchorIndex` was rewritten onto it with no behaviour change; its own tests are untouched and still pass.

**Filtering the history is CloudCLI's job here too**, and this is worth stating flatly because #25 left a note claiming the opposite ("because `revert` mutates server-side, OpenCode needs no branch filter"). Re-measured against a real 1.18.18 server and it is wrong: after a revert, `GET /session/{id}/message` still returned **all seven** messages of a seven-message session and all seven rows stayed in `opencode.db`. What changes is one column on the session row — `revert`, holding `{messageID, snapshot, diff}` — which is what `filterOpenCodeRevertedRows` reads and applies, per ADR 0007 only after the last compaction boundary, exactly as Claude's filter does. Without it the feature ships the same visible "the old messages came back" bug on reload that #25 exists to prevent. The `revert` column is part of the base `session` schema (not one of the trailing `ALTER`-added ones), so it is read without the `PRAGMA table_info` guard the token counters need.

Two things make this **two calls rather than one**, and they are the whole reason it could not ride in `buildSendOptions` the way Claude's anchor does. `resumeSessionAt` is an option on a query; `revert` is an immediate, separate operation that has to happen *before* the send. So `spawnOpenCode` intercepts: `readOpenCodeRewindAnchor(options)` reads the same `resumeSessionAt` field the frontend already sends (the websocket handler spreads unknown client options straight through, so it arrives for free), and `runOpenCodeRewindSend` performs the revert, then re-enters `spawnOpenCode` with the Anchor **stripped** — dropping it is what stops the branch being taken twice. Both the revert and the undo start and shut down the *same* short-lived headless `opencode serve` that Compact (#21) and fork (#23) use, never a third one, each with a `finally` that kills it on success, failure and throw alike. The OpenAPI-is-wrong lesson applies for the third time and was re-measured here rather than assumed: `POST /api/session/{id}/revert` is not a route, falls through to the web UI's HTML catch-all, answers **200 with an HTML body** and changes nothing — the file it should have rolled back was untouched. Only the recorded revert read *out of the body* of the legacy unprefixed route proves anything ran.

The recovery path is where measurement changed the design, and this is the part not to "simplify" later. The ticket's premise — if the send fails after the revert succeeded, call `unrevert` to put the conversation *and* the files back — is true of a **standalone** revert: measured directly, `unrevert` restored both and cleared the column. It is **not** true once the send has started, because `opencode run` **commits** an outstanding revert the moment it appends its own user message, physically deleting every reverted message and clearing `revert` — which happens well before the model call that most failures come from. A bare `unrevert` there still answers 200 with an empty `revert`, indistinguishable from having restored something, and the first version of this code cheerfully told the reader "your files are back where they were" while `tracked.txt` sat at the rolled-back contents. `undoOpenCodeRewind` therefore read the session first and only undid a revert **still standing at this Anchor**; otherwise it reported the truth — that the earlier messages are gone and the files are still rolled back. It went out with Rewind and nothing replaced the undo half: a revert that does not land now fails the run instead of pretending to recover. Silent recovery is unacceptable here, but a *false* claim of recovery is worse, and only the read tells them apart (ADR 0009; the same read is why an unreadable session is reported as unknown rather than as settled). The practical consequence for the filter above is worth knowing: because a successful send commits the revert, the window CloudCLI actually has to filter is an **outstanding** one — a revert made in OpenCode's own TUI, or one whose send failed or was aborted. Verified live in exactly that state: the provider's own API returned all 8 messages while CloudCLI's stream showed only the surviving 11 rendered messages, before and after a reload.

One deliberate gap: **Stop is unavailable for the ~1–3 s the revert takes**, because nothing is registered in `activeOpenCodeProcesses` until the CLI is spawned, so `chat.abort` answers `NO_ACTIVE_RUN` in that window. Compact registers a placeholder handle for the same reason; Rewind does not, because its window closes on its own and the ordinary run registers itself immediately afterwards. Adding one is a new decision, not a missing line.

Verified live end to end against a real OpenCode 1.18.18 session on a git working tree. The entry appeared on both user messages and none of the assistant ones; the notice read *"Sending will take the conversation back to this message. 6 messages leave the context."* followed by *"Tracked files will be rolled back to their state at that message too."*; pressing send rolled `tracked.txt` from `hello v3` to `hello v2` and continued under the **same session id**. With a revert left outstanding, a reload showed the reverted prompt gone from the stream while OpenCode's own endpoint still returned it. A forced failure (an unresolvable model) produced the honest message rather than the flattering one, matching the file on disk. And the same session after a real `/compact` rendered all of its pre-boundary history with its `Compacted` marker intact and offered **zero** Rewind entries, every user message being at or before the boundary.

## 24. Case-insensitive project path merging on Windows

**Files:** `server/shared/utils.ts`, `server/modules/file-tree/file-tree.service.ts`, `server/modules/database/migrations.ts`, `server/modules/providers/tests/opencode-sessions.test.ts`, `server/modules/providers/tests/codex-message-editing.test.ts` — all upstream-owned. *Fork-owned (new):* `server/shared/tests/normalize-project-path.test.ts`, `server/modules/database/tests/case-duplicate-project-merge.test.ts`.

**Why:** `projects.project_path` is a plain SQLite `TEXT NOT NULL UNIQUE` key with no `COLLATE NOCASE`, so comparisons are case-sensitive, but NTFS is case-insensitive-but-case-preserving and different provider CLIs report the same real directory with different drive-letter/segment casing (observed: OpenCode's session sync indexed a workspace as `D:\...` where Claude/Codex's had already indexed the identical directory as `d:\...`). The result was two disconnected `projects` rows — two sidebar entries — for one real folder, confirmed against the reporting user's own production `auth.db` (30 projects → 24 after the fix, zero duplicates left). `normalizeProjectPath()` is the single funnel already used everywhere a path becomes a DB key or comparison target, so it now lowercases the result whenever `shouldUseWindowsPathNormalization()` says the path is Windows/UNC-shaped, in addition to its existing separator/dot-segment normalization. One companion fix was needed in the same pass: `file-tree.service.ts` matched `itemPath` against `FORBIDDEN_WORKSPACE_PATHS` via `.includes(normalizeProjectPath(itemPath))`, which would have silently stopped recognizing Windows system dirs (e.g. `C:\Windows`) the moment the left side got case-folded but the list itself didn't — both sides are normalized now. A new idempotent migration, `mergeCaseInsensitiveDuplicateProjectPaths` (runs on every startup via `runMigrations`, right after `ensureProjectsForSessionPaths`), self-heals any duplicates that already exist on disk: it groups existing `projects` rows by their canonical (case-folded) path, and for every group with more than one row, repoints `sessions.project_path` to the canonical spelling and deletes the losers — done manually rather than via `ON UPDATE CASCADE`/`ON DELETE SET NULL` because the app's normal runtime connection never runs with `PRAGMA foreign_keys = ON` (`connection.ts` only toggles it transiently inside one unrelated legacy migration). The surviving row keeps `isStarred` if any duplicate had it set, `isArchived` only if every duplicate did, and the first non-null `custom_project_name`.

**On upstream conflict:** Plain bug fix in upstream-owned code, not a fork preference — same category as entries 12/14/21. **Not yet triaged against `docs/upstream-pr.md`'s bar.** If upstream fixes the same root cause (case-sensitive path-as-DB-key comparison) independently, check whether their fix also self-heals *existing* duplicate rows before dropping this — that half is easy for an equivalent upstream patch to miss, since it only shows up on an already-affected install, not a fresh one. Until then keep mine. `normalizeProjectPath()`'s case-fold is one self-contained block near the end of the function (lowercase, then re-derive `root` off the now-lowercased string) — if upstream reworks the function, re-apply that block plus the `shouldUseWindowsPathNormalization()` gate rather than the literal diff. The migration is purely additive (one new function + one call in `runMigrations`), near-zero conflict surface. The `opencode-sessions.test.ts` change is one assertion (`indexed?.project_path` now compared against `normalizeProjectPath(workspacePath)` instead of the raw mixed-case temp-dir path) — if upstream has since rewritten that test, just confirm it isn't asserting a raw, unnormalized path as the stored value. The v1.37.3 sync hit the same shape a second time in a test upstream added fresh in that release, `codex-message-editing.test.ts`'s `rewinding a Codex session moves it onto the branch and retires the old thread`: it asserts the `cwd` a rewind forks the Codex thread with, which is `session.project_path` read back out of the DB — same fix, compare against `normalizeProjectPath(workspacePath)` rather than the raw temp-dir path. Windows-only failure (the two only differ by case-folding, which is a no-op on POSIX), so it won't reproduce on Linux/macOS CI.

**Why:** Lets a CloudCLI user who has configured a direct custom voice backend (Settings → Voice, Base URL filled in — the existing upstream code path that already calls that backend straight from the browser) opt into three extra capabilities when their backend supports them, built against a self-hosted Qwen3-TTS deployment as the reference target: (1) streaming playback that starts audio from the first response chunk instead of waiting for the full download, with a stop control that actually silences already-buffered audio rather than only cancelling the network request; (2) a manual "fetch voices" action against the backend's voice-list endpoint, offered as free-text suggestions rather than a restrictive dropdown; (3) a global natural-language style/dialect "instructions" field sent on every synthesis request, streaming or not. Ticket: [#38](https://github.com/wltiger/my-cloudcli/issues/38) (spec), [#39](https://github.com/wltiger/my-cloudcli/issues/39)–[#42](https://github.com/wltiger/my-cloudcli/issues/42) (implementation). Streaming reuses the same `/audio/speech` HTTP endpoint as non-streaming (`stream:true`, `stream_format:"audio"`, `response_format:"pcm"`), not a WebSocket, to stay consistent with the fetch/AbortController cancellation model the non-streaming path already used. The backend returns headerless 24kHz/16-bit/mono little-endian PCM; `pcmAlign.ts`'s `decodePcmChunk` is the one piece with a documented, easy-to-get-wrong correctness requirement (network chunk boundaries aren't sample-aligned, so a trailing odd byte has to carry into the next chunk or every later sample corrupts into noise) and is the only part of the new streaming code with unit tests — `pcmPlayer.ts`'s actual `AudioContext` scheduling wraps it but isn't unit-tested (no such API under Node's test runner), ported from the backend vendor's own browser test page rather than designed from scratch. A response that completes having delivered zero bytes is treated as a failure (this backend's documented signature for a silently-rejected/truncated request), with no silent fallback retry to non-streaming. Streaming playback deliberately isn't cached — every repeat play re-streams — while the pre-existing non-streaming blob cache is untouched.

Getting the upstream touch points right took a real fix mid-implementation, worth recording since it's easy to reintroduce on a careless re-merge: `voicePlayer.ts`'s `toggle(content)` recomputed its own cache-key id from `content` alone, so a hook-level id computed against a wider signature (base voice config + this feature's instructions text) never matched what the player used internally — `getSnapshot()` could then never see its own in-flight `play()` as "current," so the speak button's loading/playing state stuck at idle for any non-streaming read-aloud once an instructions value was set. ## 28. Composer footer keeps its right-hand cluster on one row (the model pill yields)

**Files:** *Upstream-owned:* `src/modules/chat/composer/ChatComposer.tsx` (the footer's right-hand group — the div holding the schedule popover, model menu, permission menu and submit button — is `flex min-w-0 flex-1 ... justify-end` instead of `ml-auto ... shrink-0`), `src/modules/chat/composer/ComposerModelMenu.tsx` (the model trigger button is `min-w-0` and no longer `shrink-0`).

**Why:** v1.37.3's composer footer is a wrapping flex row (`flex-wrap`), and its right-hand cluster was `shrink-0`, so on a narrow phone the whole right side — model pill, permission, schedule, submit — wraps as one chunk onto a second row under the tools row whenever the model name is long enough for the pill to reach its `max-w-32` cap. That turns the composer into a two-row footer on any phone with a long model id. The subtle trap: a `flex-wrap` container decides its line breaks from items' **base** sizes, before any shrinking happens, so simply removing `shrink-0` does not stop the wrap — the cluster still declares a wide base size and still breaks to row two. The fix makes the wrap impossible and lets the pill absorb the shortfall: the right-hand group becomes `flex-1 min-w-0` (base size 0%, so it can never trigger a line break) and `justify-end` (its buttons stay pinned to the right edge exactly as `ml-auto` did — the `ml-auto` is dropped because an auto margin would consume the free space `flex-grow` needs). Inside that group the model pill is the only shrinkable child (`min-w-0`, `shrink-0` removed), so when the row is genuinely tight flex compresses the pill and its `truncate` label ellipsizes. The schedule/permission/submit triggers each keep their own `shrink-0`, so only the model name ever yields. Desktop is visually unchanged: there is never a shortfall, so the group just fills the row and the pill renders at natural width up to the pre-existing `max-w-32 sm:max-w-56`.

Why not just drop the footer's `flex-wrap`: the same v1.37.3 change that introduced the wrap also added the full-width submit-hint row (`order-last basis-full`, desktop only), which lands on its own row only because the footer wraps. This fork keeps that row as upstream designed it, so the wrap has to stay — which is why the fix is to make the right-hand group unable to wrap, not to make the row non-wrapping.

**On upstream conflict:** Keep mine; reapply the class changes above. If upstream restructures the footer, reapply the intent rather than the literal classes: the right-hand group must be the one that grows to fill the row (`flex-1 min-w-0`, content right-aligned) so it can never wrap, and within it the model trigger must be the only shrinkable child (its label already truncates) while the schedule/permission/submit triggers keep `shrink-0` so only the model name compresses.
