# 向官方反馈问题

决定要不要把 bug、设计缺口，或者在这个 fork 里干活时发现的技术结论反馈给 `siteboon/claudecodeui`（`upstream`）的**门槛**、流程和模板。跟 `docs/upstream-sync.md`（反方向：把 upstream 的改动拉进来）配套。这个要在主对话里交互着跑——为什么不能后台跑，见 `upstream-pr` 这个 skill 自己的说明。

## 这件事到底值不值得提

**这一节要在查重之前、在动手写任何草稿之前跑。** 门槛是**故意**设高的，默认答案是**不提**。绝大多数发现应该以一份标了 `Won't submit` 的归档草稿收场，而不是一次提交。

### 承重的判据：不提这一条，对本 fork 有成本吗？

要按这个方向问，不要反过来问。

- **某条 fork 定制在这边已经把它中和掉了。** 问题完全归上游所有；他们动不动，这个仓库都不受影响。→ **默认不提。**
- **本 fork 的行为和上游一模一样，根本不存在分歧。** 没有东西要维护，同步时也没有东西要重新应用。→ **默认不提。**
- **本 fork 背着一条每次同步都很难重新应用的分歧，上游收了就能退休这条。** → 这才是真成本，也是唯一能稳定过线的理由。

**对上游用户的严重程度，明确地不构成充分理由。** 这一条被硬案例检验过：`docs/pull-requests/PR01` 用真机实测确认，未经修改的 CloudCLI 装机上，**任何 iOS 设备从来没收到过一条推送** —— 整个平台的功能是死的、一行就能修、查重干净。它**依然没提**，因为定制 #10 在这边早就修好了。别再用"这个很严重"去翻这个决定：如果严重程度本身够用，PR01 早就发出去了。

为什么这么不对称：上游的稀缺资源是 **review 精力**，不是不知情。PR #995、#1000、#917 从 2026 年 6–7 月挂到现在没人回，其中一个提的方案跟本 fork 已经在用的一模一样。往那个队列里再加一条既不是免费的，也不见得有用。

### 如果过了上面这关，再看上游的成本和证据的硬度

下面几条**必须全部成立**，否则退回"不提"：

- **证据是实测的，不是推断的。** 任何你会写成"应该是""看起来是"的东西，必须先跑一遍看到结果。这不是空谈：PR02 的核心论断——明文 HTTP 下会显示一个假的成功 toast——**是错的**，是对着真实非安全源做浏览器实测才发现的。要是照原稿发出去，维护者第一次试就会发现描述对不上。
- **不带没验证过的调参，不带 magic number。** PR03 提的 `min-w-28` / `max-w-[22rem]` 是本 fork 自己拍脑袋的值。要么给出依据，要么从方案里砍掉。
- **不动上游刚碰过的行。** PR03 同时还改在上游三天前刚重做过样式的行上。改人家刚发布的代码，读起来像是在翻他们刚做的决定。
- **修法不需要上游做架构决定。** 如果诚实的答案是"这个 effect 得挪个地方，挪到哪是他们的事"（PR05），那它就是 triage 负担，不是一条可直接行动的报告。

### 记录结论

不管结论是什么，都在 `docs/pull-requests/` 下写一条 —— **包括把它毙掉的那次 triage**。设 `Status: Won't submit — {原因}`，并加一节 `## Decision ({日期})` 写清理由，以及**什么条件下该重新考虑**。便宜的 triage 要走在昂贵的起草前面，但只要一个发现被调查过，调查记录就留下。

**绝不要劝维护者去提。** 把 triage 结论摆出来，让他定。他的既定指令是"非必要不提" —— 拿不准就不提。

## 起草之前

只有上面那节 triage **没有**把这个发现毙掉，才走到这一节。提交之前查重仍然是硬性要求 —— 而如果一条是在没查重的情况下就归档成 `Won't submit` 的，那么条目本身和索引行**都要写明"查重没做"**，免得以后有人误当成可以直接提交的草稿。

**先查重。** upstream 自己的 `CONTRIBUTING.md` 里明文写着：*"Search first. Check existing issues and pull requests to avoid duplicating work."* 当成硬性要求，不是可做可不做——这条已经救过这个 fork 一次：避免了重新提一个 upstream 已经仔细考虑过、并且拒绝掉的方案（`siteboon/claudecodeui#1132`，被维护者一句"this is intentional"关闭、没有合并）。只搜标题不够——搜到相近的东西，要把那个 issue/PR 的正文和评论全部打开看完，不能只看标题，真正的理由通常在评论里，不在标题上。

```
gh search issues "<几种不同的说法>" --repo siteboon/claudecodeui --json number,title,state,url
gh search prs "<同样几种说法>" --repo siteboon/claudecodeui --json number,title,state,url
gh issue view <n> --repo siteboon/claudecodeui --json body,comments,closedAt
gh pr view <n> --repo siteboon/claudecodeui --json body,comments,mergedAt,closed,commits
```

至少试 2-3 种不同的措辞——能查到真正相关结果的那个说法，很少是第一次想到的那个。

**除非是一眼就能看出对错的小 bug，否则先问方向再动手。** 同样是 `CONTRIBUTING.md` 里的话：*"Discuss first for new features. Open an issue to discuss your idea before investing time in implementation. We may already have plans or opinions on how it should work."* upstream 确实说了纯 bug 修复可以直接开 PR（"Bug fixes are always welcome. If you spot a bug, feel free to open a PR directly."）——但 `#1132` 当初也是按"修 bug"的名义提的，照样在设计层面被拒了，所以只要涉及真实的设计取舍（不只是一处显而易见的改错），默认先开 issue、提出方向，而不是先把代码写出来。等维护者确认方向之后再补 PR。

## 写条目

**每一个被调查过的发现都要留一条**，不管最后提不提。工作量按 triage 结论来配：被成本判据毙掉的，只需要写清 triage、支撑它成立的证据、和结论 —— 不需要一份没人会发出去的精修 `正文草稿`。只有维护者拍板要提了，才动手写可提交的标题和正文。

第一次用到这套流程时再新建 `docs/pull-requests/`（带一个 `README.md` 索引）——不用提前建好。每条单独一个文件，不管最后是 issue 还是代码 PR 都统一编号（GitHub 的 issue 和 PR 本来就共用一套编号）：`docs/pull-requests/PR{NN}-{slug}.md`，再配一个 `.zh-CN.md` 版本给维护者自己审核用（不管中文版怎么写，里面草稿的标题/正文本身都保持英文——见下面）。

模板：

```markdown
# PR{NN}: {标题}

**状态：** 不提交 — {原因} | 草稿——待审核 | 已提交 — {链接}
**类型：** Issue | PR | —（本来会是 {Issue|PR}）
**目标仓库：** `siteboon/claudecodeui`
**发现时间：** {日期}，{背景——比如"同步这个 fork 到 vX.Y.Z 的过程中"}

## 查重
{跑过哪些搜索、试过哪些说法、查到了什么（如果有的话）、为什么那些不能覆盖这次的问题}

## 背景
{为什么是现在发现的，跟别的什么事有关联}

## 证据
{每条结论都要能对应到当前实际上线代码里的具体文件/行号——不是转述之前的研究笔记；起草这一步要重新对着 HEAD 核实一遍，从最初发现到写草稿之间代码可能已经变了。明确区分哪些是直接的代码追踪结论（"这一行代码就是这么写的"）、哪些是实测（"探测了 X，观察到 Y"）、哪些是自己的解读/推断（"这样看是这个意思，但代码没有明说"）——维护者需要知道这个区分，才知道该在哪个点上反驳。

任何承重的、一开始是推断的结论，**必须在保留之前实测掉**。如果实测跟推断相反，就地把条目改正并写明改了什么——把纠正留在文里是好事，它证明这条结论是真的被验过的。}

## Issue/PR 标题草稿 / 正文草稿
{只有维护者已经拍板要提，才写这两节。`gh issue create --body` / `gh pr create --body` 要用的原文，英文——这是真正要提交的内容，哪怕这份文件其他地方都是中文，这一块也不要翻译。}

## 提交理由
{只有真要提的条目才写这一节。}
- 查过重了（附上搜索记录）
- 证据是代码实证或实测的，不是猜的
- 定位成"报告/提问"而不是"要求"——相关的话引用 `CONTRIBUTING.md` 的"discuss first"
- 跟已知的其他事情的关系（比如某个已退休的定制项、之前被拒绝过的类似尝试）

## Decision（{日期}）
{每一条都必须有。往哪个方向走了、为什么，要落在上面那套门槛的语言里——尤其是**成本判据的哪一支**决定了结论。然后写：什么条件下值得重新考虑。如果因为先下了结论而跳过了某个必要步骤（比如查重压根没做），在这里**和索引行里都要写明**，免得以后有人误当成可以直接提交的草稿。}
```

在 `docs/pull-requests/README.md` 加一行：

```markdown
| # | Title | Type | Status | Link |
|---|---|---|---|---|
| [PR{NN}](PR{NN}-{slug}.md) ([中文](PR{NN}-{slug}.zh-CN.md)) | {标题} | Issue/PR | {状态，附一句话原因} | {提交后的 GitHub 链接，没提交就填 —} |
```

索引的开头要把这条既定门槛写在最上面，这样下次一打开先看到的就是它。

## 如果维护者反驳某个结论

要有心理准备——这是审核在起作用，不是出问题了。被反驳的时候，不要直接重申，也不要立刻让步。往下多追一层，把代码路径完整走一遍（比如从界面上的一次选择，一路追到服务端校验，再到最终传给底层 SDK/CLI 调用的那个具体参数），不要停在第一处看着像那么回事的地方就下结论。回去之后精确说清楚：现在确认了什么、之前哪里说错了、为什么。一个结论如果扛住了这种反驳，比一个从没被质疑过的结论，对最终提交来说是硬得多的证据。

## 提交之前

**把"这件事到底值不值得提"那节再读一遍。** 走到这一步，你已经在这条上投入了不少精力，而**沉没成本正是让一条不够格的发现开始显得可以提**的主要原因。triage 的结论不会因为草稿写好了就变好。

标题、正文、提交理由都要拿到明确同意，才能跑 `gh issue create` / `gh pr create`，没有例外。批准并提交之后，把这条的 `状态` 改成"已提交"，附上生成的 issue/PR 链接，文件不要删——留一份"提交了什么、后来怎么样了"的记录（合并了、被拒了、还开着）。

如果最后决定不提交 —— 这是**大多数发现的预期结局，不是失败** —— 文件也留着。把`状态`改成"不提交 — {原因}"，并把 `## Decision` 那节填上，什么都别删。之前做的核实工作是真实、以后用得上的，而且能让下一次同步不用从头再推一遍同样的结论。
