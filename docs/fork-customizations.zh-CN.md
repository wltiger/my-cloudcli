# Fork 自定义清单

**本 fork：** [`wltiger/my-cloudcli`](https://github.com/wltiger/my-cloudcli)（`origin` 远端）。**官方上游：** [`siteboon/claudecodeui`](https://github.com/siteboon/claudecodeui)（`upstream` 远端）。`main` 分支跟踪 `upstream/main`，保持干净镜像；本 fork 的所有工作——包括下面列的全部内容——都在 `dev` 分支上。完整的远端/分支/同步配置见 `docs/agents/issue-tracker.md`；具体的同步操作步骤见 `docs/upstream-sync.md`。

记录本 fork（`wltiger/my-cloudcli`）相对官方上游（`siteboon/claudecodeui`）的所有故意偏离点。以后同步 `upstream/main` 时，如果合并冲突（或者发现某处行为莫名变了）撞到下面列的文件，先查对应条目，再决定：保留自己的版本、在官方新代码上重新套一遍自己的改动，还是官方已经原生解决了这个问题、直接放弃这条自定义。

这不是待办清单——未完成的后续工作看仓库的 issue tracker（`docs/agents/issue-tracker.md`）。这份文件只负责记录"这里有个偏离点，以及为什么"。

标了 ❌ 已废弃 的条目，代码里已经没有了。条目本身保留、编号也不重排，是为了让以后的人知道曾经有过这个偏离、以及它为什么消失——通常是官方自己解决了同一个问题。想把某条捡回来之前，先读它的废弃说明。

## 3. 聊天阅读外观设置（间距 / 字号 / 宽度）

**涉及文件：** `src/components/chat/utils/chatSpacing.ts`、`chatTypography.ts`、`hooks/useChatSpacing.ts`、`useChatTypography.ts`、`view/subcomponents/ChatMessagesPane.tsx`、`MessageComponent.tsx`、`ToolGroupContainer.tsx`、`Markdown.tsx`、`ChatComposer.tsx`、`QueuedMessageCard.tsx`、`chat/tools/components/PlanDisplay.tsx`、`ToolErrorDisplay.tsx`、`ContentRenderers/MarkdownContent.tsx`、`QuestionAnswerContent.tsx`、`InteractiveRenderers/AskUserQuestionPanel.tsx`、`src/components/settings/hooks/useSettingsController.ts`、`settings/view/Settings.tsx`、`settings/view/tabs/AppearanceSettingsTab.tsx`、`src/components/quick-settings-panel/view/QuickSettingsContent.tsx`、`ForkQuickSettings.tsx`、`QuickSettingsChatSpacingRow.tsx`、`QuickSettingsChatFontRow.tsx`、`QuickSettingsChatWidthRow.tsx`、`src/i18n/locales/{en,zh-CN}/settings.json`

**为什么改：** 三个管"聊天读起来舒不舒服"的旋钮，共用同一套存储+事件机制、同一对入口（Settings 的 Appearance 标签页 + Quick Settings 面板）。三个默认值都等于官方现状，所以装上不动任何设置，界面和官方一模一样。

- **消息间距**（宽松/紧凑/无，只影响移动端）：手机屏幕小，聊天气泡左右固定的留白很浪费空间。因为这个设置在 `sm:` 断点以上是空操作，Quick Settings 那一行下面留了一句小字说明"只影响窄屏"——而不是在桌面端直接隐藏，隐藏会让人以为设置被删了。
- **阅读字号**（Small/Medium/Large/X-Large → `prose-sm`/`prose-base`/`prose-lg`/`prose-xl`，默认 Small = 官方的 14px）：官方正文在大显示器上偏小，AskUserQuestion 更糟——它内嵌模式的选项**说明**只有 11px。档位只管**阅读文字**：Markdown 正文（消息、Plan、工具错误、工具返回的 markdown）和 AskUserQuestion 的问题/选项/说明。代码块、diff、工具卡片摘要行、时间戳和徽章一律不动——代码编辑器本来就有自己的 `codeEditorFontSize`。AskUserQuestion 已有的全屏尺寸（19/18/15px）保持固定不受档位影响，且每一档内嵌值都严格小于它，内嵌永远不会反超全屏。
- **内容宽度**（标准/宽/更宽/撞满，默认标准 = 官方的 `max-w-[54.25rem]`）：侧边栏固定占 288px，868px 的内容列在 2560 屏上只用了 38%，3440 屏上只用了 28%。用户气泡最上面那个上限（`xl:max-w-xl`）也跟着档位走，免得 3000px 的列里孤零零一个 576px 气泡。只动最上面这一档：`xl` 以下列宽还没顶到自己的上限，`sm:max-w-[85%] md:max-w-md lg:max-w-lg` 这套阶梯比百分比更贴切——一刀切成 `max-w-[66%]` 反而会让 `md` 断点下的气泡**变窄**（那里列宽只有 448px，气泡本来是能占满的）。每一档的值约等于该档列宽的 66%，而这正是标准档下 `xl:max-w-xl` 算出来的比例，所以标准档和改动前一模一样。

两个值得记住的设计点：`Markdown.tsx` 是 prose 档位的唯一入口（调用点只需删掉自己的 `prose-sm`，显式传入的尺寸——比如全屏那处的 `prose-lg`——仍然优先）；缩放机制没有用 CSS `zoom`，因为 `useComposerMenuAnchor.ts` 靠 `getBoundingClientRect()` + `window.innerWidth` 算 fixed 菜单坐标，祖先带 `zoom` 会把这套算法弄错。历次迭代都并进这一条。对应 issue：[#17](https://github.com/wltiger/my-cloudcli/issues/17)。

**同步官方时怎么办：** 保留我的。纯 opt-in 设置项，加法改动。`QuickSettingsContent.tsx` 里 fork 的全部痕迹只有两行——一行 `ForkQuickSettings` 的 import，一行贴在面板 body 最末尾的 `<ForkQuickSettings />`。fork 自己加的快捷设置全部放在 `ForkQuickSettings.tsx`（官方没有这个文件）里，所以冲突后只要把那两行放回去就行，别再把新设置塞进官方自己的分组里。内容列的 `max-w` 在 `ChatMessagesPane.tsx`、`ChatComposer.tsx`（三处）、`QueuedMessageCard.tsx` 里是重复的——官方改了其中一处的话，几处必须一起同步，否则输入框会和消息列对不齐。

⚠️ **i18n 策略在这里变了。** 这一条原来写的是：所有文案用 `t(key, '英文兜底')`、不动 `src/i18n/locales/**`，让翻译文件保持零冲突面。现在不再成立：`en` 和 `zh-CN` 的 `settings.json` 已经带上了 `appearanceSettings.chatSpacing` / `chatFontSize` / `chatWidth` 这些键，中文界面因此是完整的。曾经考虑过用"fork 专属 namespace"来保持零冲突，最后否决了——`src/i18n/config.js` 把每个 namespace 的 import、`resources` 条目、`ns` 条目全部写死，新增 namespace 的冲突面**比**直接加 JSON 键**更大**。这两个文件冲突时，两边的键都保留；其余九种语言仍然一行没动，走内联英文兜底。

## 10. Web Push 的 VAPID subject 改成 APNs 能接受的值

**涉及文件：** `server/modules/notifications/vapid-keys.service.ts`

**为什么改：** 官方把 VAPID 的 `sub` 声明硬编码成了 `mailto:noreply@claudecodeui.local`。`.local` 是保留 TLD，而 APNs 会校验这个声明，于是每一条推送都被以 `403 BadJwtToken` 拒绝——**iOS 设备从来没收到过任何一条通知**。在真实环境上验证过（真机已"添加到主屏幕"并订阅成功）：同一条订阅、同一套密钥，只改 subject——`.local` → 403，`https://cloudcli.ai` → 201，换成真实的 `mailto:` → 201。Chrome 的 FCM 和 Mozilla 的 Autopush 都不校验这个域名，所以这个问题只在 iOS 上暴露，官方一直没发现。

**同步官方时怎么办：** 如果官方自己修了，就用官方的——任何可路由的 `mailto:`/`https:` 值都行，具体填什么字符串不重要。官方没修就保留我的、重新应用一遍。**已 triage，明确决定不上报** —— 见 `docs/pull-requests/PR01-vapid-subject-ios-push.md`。它确实严重（未经修改的装机上，任何 iOS 设备从来没收到过一条推送）、也确实一行就能修，但**对本 fork 零成本**，而这才是决定这类事情的判据。别再用"这个很严重"重开这个话题 —— 那个理由已经提过并被否掉了。官方一旦自己修了，这条就可以从清单里删掉。

## 12. 触屏能打开的文件树菜单 + 复制相对路径

**涉及文件：** `src/components/file-tree/view/FileContextMenu.tsx`、`FileTreeNode.tsx`、`FileTreeList.tsx`、`FileTreeBody.tsx`、`FileTree.tsx`、`src/components/file-tree/hooks/useFileTreeOperations.ts`、`utils/fileTreeUtils.ts`、`src/i18n/locales/*/common.json`

**为什么改：** 官方的文件树菜单只挂在 `onContextMenu` 上，触屏设备等于**整个菜单都打不开**——重命名、删除、下载、新建文件/文件夹、复制路径全没了。这里故意做了两个入口，方便真机上比一比再决定要不要砍掉一个：长按 500ms（手指移动超过 10px 就放弃，不影响滚动），以及每行末尾一个只在 `md:` 以下渲染的 `⋮` 按钮。两者共用同一份菜单状态；`FileContextMenu` 因此多支持了函数式 children，让每一行能自己渲染触发按钮而不用接管菜单状态。detailed 视图里手机上 `⋮` 占掉权限列——那一列本来就窄到放不下 `rw-rw-rw-` 加一个按钮。另外在官方的绝对路径"复制路径"旁边加了"复制相对路径"（两个平级菜单项，不做二级菜单），并且两个都改走项目自己的 `copyTextToClipboard`——官方直接调 `navigator.clipboard`，成功提示还是同步弹的，复制失败时会同时看到"复制路径失败"和"路径已复制到剪贴板"。

## 14. Browser 运行时装到自己管理的目录

**涉及文件：** `server/modules/browser-use/browser-use.service.ts`

**为什么改：** 官方的 `installRuntime()` 用 `cwd: process.cwd()` 跑 `npm install --no-save --no-package-lock playwright`，但 `getPlaywright()` 是从模块自身所在位置去 `require('playwright')`。全局安装的 CloudCLI 下这是两棵完全不同的树：包会装到用户当时启动 CLI 的那个目录（多半是用户主目录），而从 `<npm root -g>/@cloudcli-ai/cloudcli/dist-server/server/modules/browser-use/` 往上找 `node_modules` 永远走不到那里。结果就是装其实成功了，设置页却一直显示 `Playwright: missing`，"Install Runtime" 按钮点多少次都像没反应——每次只是往同一个够不着的地方重装一遍。现在固定装到 `~/.cloudcli/browser-use/runtime`（和已有的 `profiles/` 并列），并先写一个私有 `package.json`，免得 npm 往上找项目根、把上层目录当成自己的工程；`getPlaywright()` 则先按模块自身位置解析，找不到再从这个目录解析。`runCommand()` 为此多了一个 `cwd` 参数。manifest 既然是自己的，去掉 `--no-save --no-package-lock` 就没有副作用，留着 lockfile 重装还更快。

**同步官方时怎么办：** 这属于纯 bug 修复而不是 fork 偏好。**别人已经报给官方了** —— [#995](https://github.com/siteboon/claudecodeui/pull/995) 提的方案和这里一模一样（同一个 `~/.cloudcli/browser-use/runtime` 目录、同样的解析顺序），[#1000](https://github.com/siteboon/claudecodeui/pull/1000) 和 [#917](https://github.com/siteboon/claudecodeui/pull/917) 是同一个根因；三个从 2026 年 6–7 月开到现在都没人回。别再报第四遍（见 `docs/pull-requests/PR04-browser-runtime-install-directory.zh-CN.md`）。其中任何一个合并了，就改用官方版本并退休这条。在那之前保留我的，但要把 `installRuntime()` 和 `getPlaywright()` 当成一对看：两边必须配套才成立，官方要是改了其中一个，就两半一起重新应用，别只合一边留另一边。如果官方改成把 playwright 作为正式依赖发布，那这条整条丢掉即可——第一级解析本来就覆盖那种情况。

## 15. 移动端把标签切换栏收成一个菜单

**涉及文件：** `src/components/main-content/view/subcomponents/MainContentTabMenu.tsx`、`MainContentTabSwitcher.tsx`、`MainContentHeader.tsx`、`src/shared/view/ui/ActionMenu.tsx`

**为什么改：** 官方把标题和标签 pill 放在同一行。`lg:` 以下 pill 本来就只剩图标，但数量不固定——4 个内置，加可选的 Browser 和 Tasks，再加每个已启用插件一个——所以 375px 的手机上这排要占 148–220px，标题只剩不到 150px（6 个标签时实测 51px）。官方自己的缓解手段是给这排加横向滚动和左右渐变遮罩，能挡住溢出，但一点宽度都没还给标题。这在本 fork 里比在官方那边更亏，因为第 13 条把聊天标题变成了跨项目会话快切入口，挤窄标题等于同时挤掉一个导航入口。现在 768px 以下——用的就是 header 已经在给汉堡按钮用的那个 `isMobile`——整排收成一个约 48px 的 pill，里面是当前标签的图标加一个箭头；点开是下拉菜单，按原顺序列出全部标签，插件组前面加分隔线，当前项高亮并标 `aria-current`。标题实测宽度从 51px 变成 217px。桌面端一点没动，滚动和渐变遮罩都原样保留。

**同步官方时怎么办：** 保留我的。上游足迹刻意做得极小且全是新增：`MainContentTabSwitcher.tsx` 里一个 prop 加一个提前 `return`、`MainContentHeader.tsx` 里一行 prop 透传、以及 `ActionMenu` 上四个可选 prop（`triggerIcon`、`showChevron`、菜单项的 `iconNode` 和 `isActive`）——它原有的两处调用一个都没用到。菜单代码全在 fork 自有的 `MainContentTabMenu.tsx` 里，冲突后把那几处放回去即可。那个提前 `return` 是**故意**放在标签列表构造完之后的：两种渲染共用同一份列表，官方以后加内置标签，移动端菜单自动就有了——重新应用时别改这个位置。下拉用的是 `ActionMenu` 的 `portal` 模式，也是故意的：header 那个标签槽是 `overflow-hidden`，绝对定位的菜单会被裁掉；官方要是重构了那个容器，先确认裁剪问题再考虑换掉 portal。文案用 `t(key, { defaultValue })`，没动 `src/i18n/locales/**`（和第 3、13 条一致）。官方哪天自己做了移动端标签方案，就用官方的，把这条删掉。⚠️ v1.37.2 已经朝这个方向走了一半：标签栏现在是个正经的横向滚动条（边缘渐变、桌面端左右箭头按钮、滚轮横滚、`role="tab"` 键盘导航），移动端只在当前标签上显示文字。但那仍然是"滚动"不是"折叠"，标题拿不回宽度，所以这条先保留了——下次同步别闭眼重新应用，先在真机上对比一下再决定。

⚠️ **`MainContentHeader.tsx` 现在需要对布局本身做 `isMobile` 分支，不只是透传一个 prop。** v1.37.2 同时把 header 重构成了 `flex-col … sm:flex-row`：在 `sm:` 以下把标题和标签条各占一行，好让全宽滚动条有独立的一行。照搬过来的结果是 fork 那个紧凑 pill 单独占了一整行 —— header 从 45px 涨到 81px，标题又被压回一小截，正好跟这条定制的目的相反。所以合并后的 header 在桌面分支保留上游的 class，在 `isMobile` 时改用 `flex-row items-center` + `shrink-0`（不要 `-mx-3` 出血边距，那是给滚动条用的）。官方以后再重构 header，要重新确认 pill 还跟标题在同一行。

这个问题在浏览器 700px 下没被发现，是后来在真机上才发现的：`isMobile` 是 **<768px**，而 Tailwind 的 `sm:` 是 **640px**，所以 640–768px 这一段会同时渲染 fork 的 pill **和**上游的单行布局，看起来是对的。**移动端布局要在 ~390px 下测，不能只是"把窗口拉窄"** —— 落在两个阈值中间的视口可能同时满足两个分支，把 bug 藏起来。另外第 13 条的跨项目会话切换器已经退休，所以上面"挤压导航入口"那半个理由现在不成立了。

## 16. 推送通知按 session 收敛成一条，打开会话或在别的设备上处理完都会清掉

**涉及文件：** `server/modules/notifications/services/notification-orchestrator.service.js`、`server/modules/notifications/index.ts`、`server/modules/providers/list/claude/claude-runtime.provider.js`、`public/sw.js`、`src/components/app/AppContent.tsx`

**为什么改：** 官方给每条推送打的 tag 是 `provider:sessionId:code`，所以一个 session 只要依次触发权限请求、stop、error 三种事件，手机通知中心就会永久堆着三条通知——包括你已经在 APP 里处理过的那些，谁都不会自动消失。这个 fork 在有 `sessionId` 时把 `code` 从 tag 里去掉（变成 `provider:sessionId`）。最初想的机制——靠系统自己替换同 tag 的通知（`renotify: true`）——结果只在 Chrome/Android 上有效：iOS Safari 从来不会替换同 tag 的通知（在真机上验证过，跟 [WebKit bug 258922](https://bugs.webkit.org/show_bug.cgi?id=258922) 描述的一致），所以 `sw.js` 的 `push` 处理现在会在调用 `showNotification()` 之前，自己先把同一个 `sessionId` 已经显示的通知关掉（`closeSessionNotifications()`），不再指望浏览器代劳。在 APP 里打开该 session 时，另外会给 Service Worker 发一条 `{ type: 'CLEAR_SESSION_NOTIFICATIONS', sessionId }` 消息，复用同一个清理函数——这条路径专门兜住"没走到 tag/session 收敛逻辑"的场景。没有 session 的事件（比如 `push.enabled`）保留 `provider:global:code` 这种 tag，避免互相顶掉。另外一个独立问题：在某个设备上回答了权限请求（包括 AskUserQuestion）之后，同一条请求的推送通知会在其它每一台订阅设备上原地卡死，因为没有任何机制告诉它们"这个已经处理完了"。`chat.permission-response` 本来就是通过跟设备无关的 `resolveToolApproval()` 解析的，不管是哪个客户端发来的，所以现在这个函数会额外触发 `notifyPermissionResolved()`——一条真正、符合规范的推送（不是静默/纯数据的，那种会被浏览器判定滥用进而取消订阅），code 是 `permission.resolved`，复用同一个 session tag，通过上面的机制把"需要处理"的旧通知收敛成"已处理"。resolver 的 metadata 多了 `_userId`/`_sessionName`（跟原有的 `_sessionId`/`_toolName` 放一起），这样 `resolveToolApproval()` 不用在整条调用链上多传参数就能拿到需要的信息。

**同步官方时怎么办：** 保留我的。改动都很小很独立：orchestrator/`sw.js` 里一处 tag 表达式 + 一个 `closeSessionNotifications()` 辅助函数 + 一个 `permission.resolved` 通知函数，`claude-runtime.provider.js` 的 `resolveToolApproval()` 里加了几个 resolver metadata 字段和一次 `notifyPermissionResolved()` 调用，`AppContent.tsx` 里一个按路由 `sessionId` 触发的 `useEffect`。如果官方重做了推送 payload、tag 方案或权限批准流程，保留"每个 session 只留一条通知、打开即清、在别处处理完也会清"这个行为，照着官方的新结构重新推导 tag/清理/resolve 逻辑，别把这个功能整个丢掉。如果官方以后给别的 provider 也加上交互式审批，那个 provider 自己的 `resolveToolApproval` 等价物也需要同样的 `_userId`/`_sessionName` metadata 和 `notifyPermissionResolved()` 调用——现在只接到 Claude 上是因为目前只有它实现了 `permissions.resolve`。

## 17. Codex 模型列表改成实时拉取，不再读一份不会刷新的快照 ❌ 已废弃（v1.37.1）

**涉及文件：** `server/modules/providers/list/codex/codex-models.provider.ts`、`server/modules/providers/services/provider-models.service.ts`

**为什么改：** 官方的 `getSupportedModels()` 只读 `~/.codex/models_cache.json`——这是个不会自己刷新的时间点快照。如果用户把 Codex 走自定义 `model_provider`/中转站（通过 `~/.codex/config.toml` 里的 `model_catalog_json1` 声明），或者干脆缓存本来就旧了，就永远看不到官方新发布的模型——实测验证过：GPT-5.6 Sol/Terra/Luna 是 2026-07-09 正式发布的官方模型，而一份 2026-06-21 抓的缓存里完全没有。`@openai/codex-sdk` 的 JS API 没有对应方法能拿到这个，等价能力只存在于随包分发的 `codex` 二进制自己的 `debug models` 子命令里。这个 fork 现在会去起这个子命令的子进程（复用 `codex-runtime.provider.js` 已经在用的同一个 `@openai/codex` 二进制，通过它 `package.json` 的 `bin` 字段解析路径，保证两边版本一致），解析它的 JSON 输出；失败就退回旧的读缓存文件逻辑，再失败就退回写死的 `CODEX_FALLBACK_MODELS` 列表。同时把 `codex` 加进了 `provider-models.service.ts` 的 `UNCACHED_PROVIDERS`——不然外层那层 3 天磁盘持久化缓存会一直挡住这次刚拿到的新鲜结果，因为一次成功的缓存会被记住远超一个新模型发布的时间跨度。

## 18. Claude 模型列表改成走 SDK 实时拉取，不再是写死的列表 ❌ 已废弃（v1.37.1）

## 20. 定时触发（延后发送一条消息）

**涉及文件：** `server/modules/database/schema.ts`、`server/modules/database/index.ts`、`server/modules/database/repositories/scheduled-triggers.db.ts`、`server/modules/scheduled-triggers/`（新模块：`index.ts`、`scheduled-triggers.routes.ts`、`services/scheduled-trigger.service.ts`、`services/scheduler-poller.service.ts`、`tests/`）、`server/index.ts`、`server/modules/notifications/services/notification-orchestrator.service.js`、`.env.example`、`src/utils/api.js`、`src/components/chat/hooks/useScheduledTrigger.ts`、`src/components/chat/view/subcomponents/ComposerScheduleMenu.tsx`、`ChatComposer.tsx`、`src/components/chat/view/ChatInterface.tsx`、`src/i18n/locales/en/chat.json`

**为什么改：** 部分 Codex/Claude 中转站（第三方 API 转售服务）有自己的限流窗口，报错时给的是一句纯文本、里面点名了具体几点几分可以重试（比如"请在 今天 15:00 后再试"），而不是标准的 `retry-after` 字段。官方完全没有"等一等再重发"这个概念——session 被限流后就一直晾在那，得用户自己想起来回来手动重打字。这次加的是一个通用的、不区分 provider 的"定时发送消息"能力：任意 session 都能通过输入框旁新加的时钟图标菜单，排一条一次性的未来消息（默认内容 `continue`，可编辑）；后端每 30 秒轮询一次，到点后走的是 `chat.send` 和无浏览器的 `/api/agent` 接口本来就共用的同一个 `providerRuntimeService.run()` 入口，不需要给任何 provider 单独开后门。

轮询在真正调用 provider **之前**先把这条记录从 `pending` 抢占为 `firing`——第一版是等 provider 调用成功之后才标记，结果 provider 调用比一个轮询周期还慢的话，下一轮轮询会把它当成"还没触发过"又发一次（实测踩过：处理慢了之后，同一句 `"continue"` 被反复发进同一个正在用的 session）。因为进程崩溃卡在 `firing` 状态的记录，下次启动时会被复位成 `pending`，不会永久卡死，只是会被重新尝试。

输入框那边现在完全不做日期选择——只有一个时间框。裸的 `HH:mm` 永远表示"这个钟点接下来最近一次出现"：还没到就是今天，已经过了就是明天（最多推 24 小时），而且这个判断是**每次渲染都重新算的**，不是算一次存起来。早期版本是在 `onChange` 里算好存起来的，但原生时间输入框按段（先时、后分）多次触发 `onChange`，不是等你输完才触发一次——输到一半的中间值只要恰好判成"过了"，就会永久锁定成明天，哪怕你后面输完的时间其实还是今天。现在旁边只会有一个纯展示、不能点的"Tomorrow"文字提示，故意不留任何选具体日期的入口。5 个快捷预设覆盖常见场景：`+10min`/`+60min`（可以连续点——每次都是在当前草稿基础上累加，不是从"现在"重新算）、下一个整点、下一个 `{0,3,6,9,12,15,18,21}` 间隔点，以及固定的 `00:05`"明天一早"快捷方式。每次重新打开这个弹层，都会回到一个全新的默认值，不会停留在上一次打开/已提交/已取消时的状态上。

这一版刻意只做手工、一次性的基础能力——"自动识别中转站限流文案、自动建一条定时"是明确留到后面做的扩展，这次不实现。触发是无头(headless)执行的（没有真实 WebSocket 客户端连着），所以如果凑巧开着这个 session 的页面，看不到回复实时流式进来——页面只会通过一条 `session_upserted` 广播感知到"这个 session 变了"，而前端现在把这条事件当成只更新侧边栏用，没有处理成"刷新当前打开的会话"；把无头触发的结果真正实时推进已打开的页面，这次没做。定时时间到了但服务当时没在跑（比如电脑关机）：只在一个可配置的宽限窗口内（`SCHEDULED_TRIGGER_GRACE_WINDOW_MINUTES`，默认 60 分钟）补发，超过宽限窗口就标记为 `expired`，不会悄悄丢掉，也不会不管多久之前的都硬发一条出去。

**同步官方时怎么办：** 保留我的。新增一张表 + 一个独立模块，本身冲突面很小；唯一会碰到官方也在维护的文件的地方都是纯增量式的（`schema.ts` 里 `INIT_SCHEMA_SQL` 末尾追加一段 `CREATE TABLE IF NOT EXISTS` + 两条索引，`database/index.ts` 里加一行 repository 导出，`server/index.ts` 里加一个 import + 两行路由挂载/轮询启动，`ChatComposer.tsx` 里在已有的 `ComposerPermissionMenu` 旁边加一个 `ComposerScheduleMenu` 位置，`ChatInterface.tsx` 里多传一个 `sessionId` prop，通知模块的 orchestrator 里加两条 `CODE_MAP` 文案)。如果官方改了 `chat-websocket.service.ts` 里 `runtimeOptions` 的拼法（从 session 行取 `cwd`/`projectPath`），要同步改一下 `scheduled-trigger.service.ts` 的 `fireTrigger()`——这段是特意从那边抄过来的，没有抽成共用函数。如果官方以后做了真正的"无头触发结果推进已打开页面"机制，这里应该改用官方的，而不是继续用现在这个只更新侧边栏的 `session_upserted` 广播。

## 21. 宽表格改成横向滚动，不再挤成一团

**涉及文件：** `src/components/chat/view/subcomponents/Markdown.tsx`

**为什么改：** 官方的表格渲染是外层 `overflow-x-auto` 配上 `min-w-full` 的表格。CSS 的 auto 表格布局只有在内容**再也没法换行**时才会溢出容器，所以一张普通文字的表格会把每一列压缩到接近"最长的那个单词"的宽度，而不是溢出——外层因此没东西可滚，文字挤到看不清。（如果表格里全是长的不可断开的串，它反而会溢出并正常滚动，所以这个 bug 看起来时有时无。）加上 `w-max` 让表格按自然宽度撑开，外层才真的能滚；`th`/`td` 上的 `min-w-28`/`max-w-[22rem]` 防止单列塌掉或者撑太宽；`overscroll-x-contain` 防止在表格里横滑时把后面的整页也一起带走。

**同步官方时怎么办：** 这不是 fork 偏好，是纯 bug 修复，但**已 triage，明确决定不上报**（见 `docs/pull-requests/PR03-markdown-table-horizontal-scroll.md`：上游刚重做过这几行，而且宽度上下限是本 fork 没验证过的拍脑袋取值）。官方哪天自己修了就把这条删掉。在那之前保留我的，但要**合并、不要替换**：v1.37.2 重新设计了这几行的样式（圆角边框容器、单元格去边框、用 `my-0` 抵消 Tailwind Typography 的表格外边距），整段用 fork 这边覆盖会把这些静悄悄地退回去。做法是采用官方的 class，再把宽度/overscroll 这四个 class 加回去。

## 22. Compact：压缩会话上下文（压缩边界标记、入口、OpenCode）

**涉及文件：** `server/shared/types.ts`、`server/modules/providers/list/claude/claude-sessions.provider.ts`（+ 测试 `server/modules/providers/tests/claude-sessions.test.ts`）、`server/modules/providers/services/provider-capabilities.service.ts`（+ 测试 `server/modules/providers/tests/provider-capabilities.service.test.ts`）、`server/modules/providers/list/opencode/opencode-runtime.provider.js`（+ 测试 `server/modules/providers/list/opencode/opencode-runtime.provider.test.js`）、`server/modules/providers/list/opencode/opencode-sessions.provider.ts`（+ 测试 `server/modules/providers/tests/opencode-sessions.test.ts`）、`src/stores/useSessionStore.ts`、`src/components/chat/types/types.ts`、`src/components/chat/hooks/useChatMessages.ts`、`src/components/chat/hooks/useChatProviderState.ts`、`src/components/chat/hooks/useChatComposerState.ts`、`src/components/chat/hooks/useSlashCommands.ts`、`src/components/chat/utils/compactCommand.ts`（+ 测试 `src/components/chat/utils/compactCommand.test.ts`）、`src/components/chat/view/ChatInterface.tsx`、`src/components/chat/view/subcomponents/MessageComponent.tsx`、`src/components/chat/view/subcomponents/CommandResultModal.tsx`、`src/i18n/locales/{en,zh-CN}/chat.json`

**为什么改：** 在输入框里敲 `/compact` 其实早就能送到 provider 并真的完成压缩——问题在于 Claude session 的 normalizer 把所有 `type: "system"` 事件都悄悄丢掉了，所以压缩结果一直看不见，`/compact` 看起来就像坏的。这个能力缺口是官方自己的，但补齐它用的是本 fork 自己出的设计方案（issue [#18](https://github.com/wltiger/my-cloudcli/issues/18)），所以记在这里，不能假设以后同步官方时会自动补上。工单 [#19](https://github.com/wltiger/my-cloudcli/issues/19)（这条记录的第一部分）让 Claude Agent SDK 发出的压缩边界变得可见：给 `normalizeMessage` 加一个分支，识别 `type: "system", subtype: "compact_boundary"`，产出一个新的 `compact_boundary` 规范化消息种类，带上触发方式（`/compact` 手动触发是 `manual`，provider 自己触发是 `auto`）和压缩前后的上下文 token 数。这个事件在线上有两种不同的字段形状，得在同一个分支里都认出来：SDK 实时查询流用的是下划线命名（`compact_metadata.pre_tokens`），落盘的 JSONL 会话记录用的是驼峰命名（`compactMetadata.preTokens`）——同一个分支两种都读，这样刷新页面后标记还在。前端把它渲染成**chrome**（术语见 `CONTEXT.md` 的 glossary），直接复用现有任务通知行（`MessageComponent.tsx` 里的 `isTaskNotification` 分支）一样的视觉分量，没有另起一套样式。

工单 [#20](https://github.com/wltiger/my-cloudcli/issues/20) 让本来就能用的 `/compact` 变得可发现、可点击，并按 provider 开关。`provider-capabilities.service.ts` 多了一个能力位 `supportsCompact`（claude 和 opencode 都是 `true`——opencode 靠的是下文 [#21](https://github.com/wltiger/my-cloudcli/issues/21) 加的旁路；codex 按 ADR 0004 是 `false`；cursor 是 `false`，还没调查）——在 `useChatProviderState.ts` 里只解析一次（`currentProviderSupportsCompact`），再分别传给 `useSlashCommands.ts`（控制补全菜单里的条目）和 `CommandResultModal.tsx`——后者拿到的已经是解析好的 `onCompact` 回调，不支持时为 `undefined`（以此控制 token 用量面板里的按钮），两处都不再各自重复判断 provider id。`/compact` 这条补全菜单条目本身完全是前端拼出来的——后端没有对应的命令——菜单展示用的 `namespace` 是 `builtin`，但路由用的 `type` 是 `compact`。这个条目由 fork 自有的辅助文件 `compactCommand.ts` 拼装，再通过 `useMemo` 合进取回的命令列表，而**不是**放在取数的 effect 里：能力位是在命令列表**之后**才解析出来的，让那个 effect 依赖它会导致每次打开会话时 `/api/commands/list` 和 provider skills 接口各被请求两次。把这段逻辑单独放一个新文件，也顺带让它不落在官方拥有的代码行上。有两处已有的判断条件因此各多了一个子句，而不是被重写：`useSlashCommands.ts` 的 `isSkillCommand` 判断（这样从菜单里选中 `/compact` 时只是把它填进输入框，而不是像其他内置命令那样发去后端命令接口执行——和 skill 命令的待遇完全一致）；`useChatComposerState.ts` 的斜杠命令拦截判断（这样提交 `/compact` 时会原样送到 provider，而不是被拦成一次 UI 动作）。token 用量面板的 Compact 按钮放在 `CommandResultModal.tsx` 弹窗底部、Close 按钮旁边，不管面板内容多高，在小屏幕上都够得着、点得到；点击后调用的是 `useChatComposerState.ts` 里新加的 `triggerCompact`，它把 `/compact` 写回输入框，再走 `handleCustomCommand` 处理自定义命令时已经在用的那套"写回再提交"机制——同样绕开后端命令接口，因为那边根本没有 `/compact` 的处理器可以路由过去。`useChatProviderState.ts` 自己那份前端能力镜像，故意没有给 `supportsCompact` 配一张按 provider 猜的兜底表（不像 `supportsEffort` 那样有兜底表）：在 `/api/providers/capabilities` 请求返回之前，或者这次请求失败时，所有 provider 一律按不支持处理，这样按钮宁可迟一点出现，也不会先冒出来再点不动。

工单 [#21](https://github.com/wltiger/my-cloudcli/issues/21) 落地了 `supportsCompact` 在 OpenCode 这边的部分。OpenCode 没有类似 SDK 那种内联压缩的东西：`opencode run` 的位置参数消息是纯文本，不会展开斜杠命令（针对 1.18.18 验证过），所以 `/compact` 永远不可能作为 prompt 发到模型那边去；真正能触发压缩的接口只挂在 OpenCode 的 HTTP server 上，一次性的 CLI 完全碰不到。这个旁路整个都写在 `opencode-runtime.provider.js` 的 `spawnOpenCode` 里，是它原来 `return new Promise(...)` 之前多出来的一个提前 return：当收到的原始命令正好是 `/compact` 时，`runOpenCodeCompactSideChannel` 会先起一个短命的无头 `opencode serve --port 0 --hostname 127.0.0.1`（OpenCode 的 session 是全局存储的，所以随便哪个 server 实例都能访问任意 session——#18 里验证过，在不相关的目录起一个 server，照样能列出别的项目的 session），等 server 自己在 stdout 里确认已经在监听（这行日志只有 socket 真的开始接受连接后才会打出来，所以不用另外再轮询一次判断是否就绪），然后 POST 到那个没有前缀的老接口 `/session/{id}/summarize`，body 是 `{providerID, modelID}`，这两个值是从一次性路径本来就会调用的 `resolveResumeModel` 结果里拆出来的——不是另外发起一次查找。server 保证一定会被关掉：如果 server 一直没能进入监听状态（起进程失败、提前退出、或者 15 秒启动超时），`startOpenCodeServeProcess` 会在 reject 之前自己把进程杀掉；如果 server 顺利进入监听状态，调用方的 `finally` 会在它之后负责杀掉，不管后面那次 POST 是成功、失败还是直接抛异常。**`killOpenCodeProcessTree` 不要简化成一句 `.kill()`。** Windows 上 cross-spawn 会把 `opencode` 解析成 `.cmd` shim，而这种 shim 只能经由一层 `cmd.exe` 执行；对最外层这个进程发信号，底下真正的 `node`/`bun` server 以及它占的端口会被遗留成孤儿，因为 Windows 不会把终止级联给子进程。这是实际观察到的：直接发 `SIGTERM` 之后，临时 server 的端口还在监听。所以 Windows 分支会去调 `taskkill /pid <pid> /T /F`，POSIX 分支则在 5 秒后把 SIGTERM 升级成 SIGKILL，形状照搬 plugins 模块的 `stopPluginServer`。两个分支都有超时上限，避免杀不掉时让等待中的旁路永远悬着。另外旁路运行期间会往 `activeOpenCodeProcesses` 里注册一个句柄，这样压缩进行中点 Stop 也能像中断普通运行那样中断它。下面那条一次性的 `opencode run` 路径完全没被碰。

这里也顺带把 #18 最初调研时记错的两个接口，按针对真实 1.18.18 session 实测的结果（详见 [#21](https://github.com/wltiger/my-cloudcli/issues/21) 的评论）直接写死进了 runtime 里：`POST /api/session/{id}/compact`——#18 最早是从 OpenCode 自己的 OpenAPI 文档里看到这个接口的——在 1.18.18 里只是声明了，并没有真的实现，调用会返回 `503 {"message":"Session compact is not available yet"}`。真正能用的是没有前缀的 `POST /session/{id}/summarize`。更坑的是，`/api/session/{id}/summarize`（对着老接口猜出来加了前缀的版本）压根不是一个路由——它会落到 web UI 的 HTML 兜底页上，返回 `200` 和一段 HTML，如果只看状态码很容易被这个假成功骗过去。`runOpenCodeCompactSideChannel` 一定会去解析响应体，并且要求它就是 JSON 字面量 `true`；不管是非 2xx 状态码，还是解析不出来/不是 `true` 的响应体，都会被当成失败处理，所以这个 HTML 兜底的坑会直接报错，而不是被误判成静默成功。

`opencode-sessions.provider.ts` 在 `normalizeHistoryRows` 里，`text`/`reasoning`/`tool`/`patch`/`agent` 这几个已有的 part 类型判断后面，追加了一个新分支 `compaction`。OpenCode 把一次压缩存成一个 `{type: "compaction", auto: boolean}` 的 part——没有 token 数，这点和 Claude SDK 的事件不一样——挂在它自己合成的一条 user 角色消息上，这条消息没有配套的 text part；紧跟在后面的摘要是一条普通的 assistant 文本消息，不需要任何特殊处理（这是 OpenCode 这边对应 Claude `isCompactSummary` 标记的东西，但这边原有的 `text` 分支本来就能把它正常渲染出来）。因为这个循环是按 part 分发而不是按 message 分发，那条没有文本的 user 消息永远不会走到上面的 `text` 分支，所以"空 user 气泡"这个坑根本不需要额外写代码去防——原来按 part 分发的循环结构本身就已经把它挡在外面了。`auto` 会映射到 #19 引入的同一个 `compactTrigger` 字段上（`false` → `manual`，这是目前从旁路里唯一观察到的值；`true` → `auto`，对应 OpenCode 自己触发压缩的情况，目前还没实测到过）。`compactPreTokens`/`compactPostTokens` 保持 undefined，#19 的渲染逻辑本来就会在这种情况下只显示触发方式。

**同步官方时怎么办：** 保留我的。官方那边压根没有"压缩可见"这个概念——`/compact` 在官方那边也是看不见的——所以这次改动大部分是全新代码、落在全新位置（整个 `compact_boundary` 分支、i18n key、新增的 switch case、新的补全条目和面板按钮），基本没有需要合并的重叠部分。真正的风险点是官方自己也在改的那几个共享分发点，这次在每一个上面都只加了一小块，如果官方那边结构变了，重新按"同样的形状"补一刀，而不是照搬这次的字面 diff：`server/shared/types.ts` 里的 `MessageKind` 联合类型只是在末尾追加了一个成员（`compact_boundary`）——冲突解决时不要把它排到别处去；`claude-sessions.provider.ts` 的 `normalizeMessage` 只是在算出 `baseId` 之后插入了一个分支——不要借机把周围的 if 链"顺手重构"一下；`useChatMessages.ts` 的 `switch (msg.kind)` 在 `task_notification` 旁边加了一个 `case`；`MessageComponent.tsx` 渲染用的三元链在 `message.isTaskNotification` 旁边加了一个分支。`server/shared/utils.ts` 的 `createNormalizedMessage` **完全不需要改**——它本来就是泛化地透传各种消息种类专属字段的，这也是为什么最终只涉及四个前后端文件而不是五个。

工单 #20 直接碰了一个风险更高的文件：`useChatComposerState.ts` 体量大，官方也在持续改。它一共多了四样东西，全是追加、没有挪动任何已有代码：拦截判断上的一个子句（`&& matchedCommand.type !== 'compact'`）、`triggerCompact` 回调、`UseChatComposerStateArgs` 上的 `currentProviderSupportsCompact` 入参及其解构、以及返回对象上的 `triggerCompact`。如果官方那边拦截那一行已经变了，照样只补那个子句到新的条件里，不要照搬字面 diff。`useSlashCommands.ts` 的 `isSkillCommand` 同样只追加了一个 `|| command.type === 'compact'` 子句。`provider-capabilities.service.ts` 的 `ProviderCapabilities` 类型和 `PROVIDER_CAPABILITIES` 里每个 provider 的对象都只追加了一个 `supportsCompact` 字段——保持它在最后，冲突解决时不要把矩阵顺序打乱。`useChatProviderState.ts` 多了一个能力 getter，`getSupportsCompactForProvider`，参照的是已有的 `getSupportsEffortForProvider`，但故意没有照抄它的按 provider 兜底表这部分（原因见上面"为什么改"）——不要"顺手"把它改成跟那个一样。`CommandResultModal.tsx` 的底部按钮区加了一个条件渲染的按钮，挨着 Close。

**为什么改：** 在 Claude 会话里，用户可以从任意一条消息发起 **Fork**——这个词以及本条目大量用到的 **Anchor**、**Transcript row**、**Compact**，定义都在 `CONTEXT.md` 的术语表里。到那条消息为止的对话会被复制成一个全新的会话（有自己的 id），原会话完全不动，仍然可以继续跑。官方完全没有这个概念。工单 [#22](https://github.com/wltiger/my-cloudcli/issues/22)；这是一组五个工单的打头阵那个（[#23](https://github.com/wltiger/my-cloudcli/issues/23) OpenCode fork、[#24](https://github.com/wltiger/my-cloudcli/issues/24) Clear、[#25](https://github.com/wltiger/my-cloudcli/issues/25) Claude rewind、[#26](https://github.com/wltiger/my-cloudcli/issues/26) OpenCode rewind），所以这里的代码大部分是给后面几个工单留的接缝，而不是那个按钮本身。

最关键的一个决定是：**Anchor 在后端算好，跟着每条消息一起发给前端**，作为 `NormalizedMessage` 上一个新的可选字段 `anchor`。前端推不出来：`normalizeMessage` 造的是拼接出来的 id（`${baseId}_tr_${tool_use_id}`、`${baseId}_text_${partIndex}`、`${baseId}_text`、`${baseId}_images`），前端手里拿到的从来就不是一个干净的 transcript uuid——何况一条渲染出来的消息本来也不等于一行 transcript row。`claude-anchors.ts` 是一个 fork 自有的纯函数 `buildClaudeAnchorIndex(rows)`，输入原始 JSONL 行，输出「行 uuid → anchor uuid」，`fetchHistory` 再把每条归一化消息打上它所属那行的 anchor。有三个实测出来的事实决定了它的形状，全部是拿真实 transcript 和 SDK 0.3.165 验过的，不是看文档抄的：(1) 一个 agent turn 会写成好几行——推理、正文、每个工具调用各一行——它们共享同一个 `message.id`，而 `forkSession` 的 `upToMessageId` 是**闭区间**，所以一个 turn 的 anchor 是它的**最后一行**；锚在第一行会悄无声息地把这个 turn 截断。(2) 这些行**不一定挨在一起**：一条 assistant 消息发起两个工具调用时，每个工具结果会写在它对应的两行 `tool_use` 中间，所以分组要按整份 transcript 的 `message.id` 来，而不是按连续段——按连续段分组能通过简单场景，却会悄悄把并行工具那种情况劈成两半。(3) **最后一个压缩边界**及其之前的每一行一律没有 anchor，前端也就不会给出入口：Compact 之前的 Rewind anchor 已知会硬失败（`resumeSessionAt` → `No message found with message.uuid of: …`），Fork 能不能扛住没测过，所以两者都走保守规则。实测确认过：在一个跑过两次 `/compact` 的会话里，边界及之前的每条消息拿回来都没有 anchor，边界之后那条有。

Fork 本身是一次**纯文件操作**——SDK 复制 transcript、重映射每一个 uuid、保留 parent 链，把 `<新会话id>.jsonl` 写在原文件旁边的同一个 project 目录里，既不跑模型也不花 token。`dir` 传的是**工作区路径**，也就是会话行里存的 `project_path`，不是 `~/.claude/projects/...` 那个目录。因为 uuid 被重映射了，fork 自己的 anchor 是从它自己的文件重新算出来的，跟源会话的不一样——这也正是 anchor 任何地方都不做持久化的原因。

provider 这一侧的接缝是给 `IProviderSessions` 追加的一个**可选**方法 `forkSession?`，这是刻意的，没有在 service 里按 provider 写 `if`：各家对「被锚定的那一行是保留还是丢掉」意见不一致（OpenCode 自己的 fork 不含那一行，而它的 revert 含），所以这件事归各自的实现管，#23/#26 也按同样方式加自己的。`session-fork.service.ts` 负责所有跟 provider 无关的部分：通过 `providerRegistry` 解析 provider、调用 facet、然后把复制出来的会话登记进库。登记是三次 `sessionsDb` 调用，每一次都不能省——`createAppSession`（分配 app 侧 id + fork 的名字）、`assignProviderSessionId`（记录映射，并把 watcher 可能已经建好的那行合并掉），然后再调一次 `createSession(...)` 纯粹是为了写 `jsonl_path`：这件事 sessions watcher 下一轮扫描本来也会做，但 fork **当下**就需要它，否则打开是空的。app-session 这个形状（`session_id` ≠ `provider_session_id`）不是好看而已：`createSession` 里 `custom_name` 的 CASE 只有在两者不同时才保留原名，所以如果直接用 provider id 登记这个 fork，下一轮同步就会把 `[Fork] …` 覆盖成按第一条用户消息推出来的标题。model 和 reasoning effort 从源会话行复制过来，fork 才能用同样的运行配置接着跑。

命名对话框预填 `[Fork] <原会话名>`，同一个 project 下（含已归档会话）该名字已被占用时加序号（`(2)`、`(3)`，中间有空缺会补上）。这个建议名是在**后端**算的（`GET /sessions/:sessionId/fork-name`），因为前端的 project 数据是分页的、手里只有第一页的名字，判断不了哪些被占了；hook 是**先**取到名字再打开对话框，所以输入框不会先空一下或者先显示一个错的名字。`buildForkSessionName` 单独导出，纯粹是为了让命名规则被测试钉住。确认之前什么都不会创建——已验证：点取消后数据库零新增行、磁盘零新增 transcript 文件。

前端这边 `supportsFork` 完全照抄条目 22 里 `supportsCompact` 的做法，包括它那条**不做兜底猜测**的规则：在 `/api/providers/capabilities` 返回之前，`getSupportsForkForProvider` 对所有 provider 都读作 false，入口宁可先藏着，也不要在一个不支持 fork 的 provider 上先闪一下。`src/` 里没有任何按 provider 分支的代码——一条消息要么带 `anchor`，要么不带。`anchor` 走的是 `useChatMessages.ts` 里的 `sharedMetadata`（那个会被展开进每一种消息分支的对象），而不是某个 `case`，因为它对所有类型都适用。有请求在跑时入口也会藏起来（`!isProcessing`），这顺带盖住了唯一一个真实的缺口：**实时流过来的消息没有 anchor**，因为一个 turn 的 anchor 要等这个 turn 的最后一行出现才知道。这个缺口会自己恢复，不需要额外代码——sessions watcher 发现 transcript 变了，聊天面板重新拉历史，跑完的那个 turn 就拿到 anchor 了；这一点直接观察过：往一个 fork 里发一条消息，几秒后新的那个 turn 就可以被 fork 了。确认 fork 之后走 `handleSessionEstablished` 切过去，跟新建会话是同一条交接路径，侧边栏不需要第二套并行逻辑；fork 之后改名用侧边栏已有的行内重命名，没有再造第二个改名功能。

还有一个**前置重构**跟这次一起进来了，单独拿出来说一下：`claude-sessions.provider.ts` 里原本有个模块内的 `async function getSessionMessages(...)`，名字跟 SDK 自己的 `getSessionMessages` 导出撞车，而 #25 需要把那个导出 import 进同一个文件（见 ADR 0007）。现在改名为 `readClaudeTranscriptRows`，顺带也更贴切。

工单 [#23](https://github.com/wltiger/my-cloudcli/issues/23) 落地了 OpenCode 这一侧的 `supportsFork`，也正是这个工单证明了「anchor 是各家自己的不透明 token」这个设计是对的。`opencode-anchors.ts` 是**第二个、平行的** fork 自有纯函数 `buildOpenCodeAnchorIndex(rows)`——刻意没有把 Claude 那个抽象成通用版本，因为两边的规则本身就不一致。拿真实的 1.18.18 会话实测：`POST /session/{id}/fork {messageID}` 是**开区间**的，生成的会话停在传进去那条消息**之前**（用收尾那条 assistant 消息去 fork，结果把这个 turn 的回复正文丢掉了）。OpenCode 跟 Claude 一样会把一个 turn 拆成好几条消息——一个写文件的 turn 回来是两条 assistant 消息，一条带工具调用、一条带回复正文——所以「anchor 是这个 turn 的末尾」这条推理照样成立，但开区间把它往后挪了一格：**一个 turn 的 anchor 是*下一个* turn 的第一条消息**，而 Claude 的是这个 turn 自己的最后一行。这里说的一个 turn，指的是「单独的一条用户提问」或者「连续的一串 assistant 消息」；锚在下一条*消息*而不是下一个 *turn* 上，简单场景能过，用了工具的那种会被悄悄截断。而 OpenCode 自己的 `revert`（#26）又反过来**包含**传进去的那条消息——同一个 provider，两条相反的约定——这正是 anchor 必须是各 provider 自己的不透明 token、绝不能合并成一条通用规则的原因。

最新的那个 turn 后面没有消息可以指，所以它拿到的是 `OPENCODE_SESSION_END_ANCHOR`，一个该模块导出的哨兵值：实测 `POST .../fork` **完全不带** `messageID` 时会把整个会话复制一份，这正好就是「停在最后一个 turn」。没有它的话，入口恰好会在大家最常 fork 的那几条消息上消失。anchor 是在 `normalizeHistoryRows` 里通过一个一行的 `push` 闭包打上去的，而不是改它那七个 emit 点；最后一次压缩及其之前的消息一律没有 anchor——跟 Claude 那边是同一条保守规则，也是条目 22 加的那个 `compaction` part 分支在这里被第二次用到的原因。

要够到这个接口，复用的是 Compact（[#21](https://github.com/wltiger/my-cloudcli/issues/21)）已经起过的**同一个**短命 headless `opencode serve`，而不是再起一个：`forkOpenCodeSession` 现在住在 fork 自有的 `opencode-serve.ts` 里，通过 `withOpenCodeServe` 借用 runtime provider 自己的 `startOpenCodeServeProcess`/`killOpenCodeProcessTree`——「起服务、用服务、关服务」这一套只写了这一处，无论成功、失败还是抛异常都会把服务器关掉，而且四个调用方（Compact、fork、revert、unrevert）现在都走它。`opencode-sessions.provider.ts` 里的 `forkSession` facet 方法就只有这一次调用——sessions facet 去 import `opencode-serve.ts` 是刻意的，正是这一点保证了 headless 服务器只有一份实现。#21 那条「OpenAPI 文档写的路由不算数」的教训在这里原样成立，而且重新测了一遍：`/api/session/{id}/fork` 根本不是一个路由，会落到 Web UI 的 HTML 兜底上、返回 `200` 加一坨 HTML，所以只有从旧的无前缀 `/session/{id}/fork` 的**响应体**里读出一个会话 id，才算真的 fork 成功了。最后，这个接口**不接受标题**——OpenCode 会把复制出来的会话叫做 `<原标题> (fork #1)`——所以 `[Fork]` 这个名字是事后单独发一次 `PATCH /session/{id}` 带 `{title}` 改的，并且从响应里把标题读回来确认；改名没生效只打一条 warning，不会因此把 fork 丢掉，反正 CloudCLI 显示的是它自己那份名字。已经端到端验过：在对话中间 fork，复制出来的会话正好停在选中消息所在 turn 的**末尾**（工具调用和回复正文都在，后面那个 turn 一点没带过来）；在最新那条消息上 fork，整个会话都复制过来了；两个 fork 在 OpenCode 自己的会话列表里都叫 `[Fork] …`；原会话消息一条不少，而且还能继续跑。

工单 [#24](https://github.com/wltiger/my-cloudcli/issues/24) 加的是 **Clear**——这个词同样看 `CONTEXT.md` 的术语表。它是这一组操作里唯一**完全不碰任何 provider 接口**的一个，所以 Claude 和 OpenCode 在同一个工单里一起拿到了它，代码里也没有任何按 provider 分支的地方。决定见 ADR 0005，它取代了 ADR 0003：0003 原本打算把 Clear 做成「rewind 到零」，实测在 Claude 上做不到——`resumeSessionAt` 遇到任何解析不了的 uuid 会直接硬失败（`No message found with message.uuid of: …`），而第一条用户消息的 `parentUuid` 是 `null`，它前面根本没有可以锚定的行。所以 Clear 不能用 Rewind 表达。OpenCode **可以**原地清空一个会话（拿第一条消息去 `POST /session/{id}/revert`，甚至能用 `/unrevert` 撤销），这条路是**刻意不用**的：同一个按钮在一个 provider 上会多出一条侧边栏记录、在另一个上不会，比两边都一样要糟。

后端全部就是 `session-clear.service.ts`：把当前会话改名成 `[Cleared] <原名>`、归档它，然后在同一个 project 下建一个空的 app 会话。有三处是设计的承重点：

- 前缀是一个**写进 `custom_name` 的固定英文字面量**，不是翻译字符串，也不是渲染出来的徽标——这样切换语言它还在，侧边栏已有的行内重命名也能直接改它。`buildClearedSessionName` 单独导出纯粹是为了让规则被测试钉住；对一个已经 Clear 过的会话再 Clear 一次，前缀是**叠加**的（`[Cleared] [Cleared] …`），跟 `buildForkSessionName` 的做法一致，而不是把前缀吃掉。
- 归档之所以能一直有效，**只是因为那行退役的记录再也不会被写第二次**。`createSession` 的 upsert 每次写入都会把 `isArchived` 重置成 0，而同步器是增量的：没人碰它，它就一直是归档状态；用户一旦回去继续这个会话，它**自己就会取消归档**。这个自愈是特性，所以刻意没有写任何「保持归档」的特例。两个 provider 都验过：回到一个退役会话继续发消息，几秒之内它就回到了活跃列表里，走的就是普通的 sessions watcher upsert，没有别的。实测的一个小例外：本来就是 provider 形状的会话，在被恢复的同一时刻也会丢掉 `[Cleared]` 前缀—— upsert 里的 `custom_name` CASE 只在 `session_id` ≠ `provider_session_id` 时才保留名字。标记和归档一起消失，读起来是对的，但这也意味着前缀只在 app 形状的会话上才撑得过一次恢复。
- 那个空会话建出来时**完全没有名字**——`sessionsDb.createAppSession` 不传 `customName`——这跟 #22 踩的坑正好是镜像的两面。它既要是 app-session 形状（`session_id` ≠ `provider_session_id`），`custom_name` 又必须是 NULL，因为 upsert 里 `custom_name` 的 CASE 只有在名字还是 NULL 时才允许同步出来的标题落进去；如果改走会话网关的 `buildCloudCliSessionName('')`，这个新会话就会被永远钉死在 “Untitled Session” 上。model 和 reasoning effort 会从退役的那个会话复制过来，用户接着用的还是原来那套运行配置。

`supportsClear` 完全照 `supportsCompact`/`supportsFork` 的先例来，包括那条不做兜底猜测的规则。因为压根没有 runtime 参与，这个标志记录的是 Clear 在哪些 provider 上**验证过**，而不是哪个 runtime 能做什么：Claude 和 OpenCode 为 true，Codex 和 Cursor 只是没验过。标志为 false 的 provider 会被 service 拒掉，所以这个能力位不是摆设。

前端这边，Clear 是**输入框斜杠命令菜单里的一项**——不是侧边栏操作，也不是挂在每条消息上的按钮。`clearCommand.ts` 照着 `compactCommand.ts` 写，但刻意是第二个函数而不是把它抽象成通用版本，因为两者对「选中它意味着什么」的答案是相反的：Compact 必须原样送到 provider，Clear 必须永远不离开 CloudCLI。两条入口路径——从菜单里点，和手打 `/clear` 再发送——都汇到 `executeCommand`，所以在这个函数最上面加一个分支就同时盖住了两条，也保证 `/clear` 不会跑到 `/api/commands/execute` 去；已实测手打 `/clear` 同样能把会话退役，日志里没有任何命令执行错误。如果项目里已经有一个同名命令，它优先：这一项直接跳过，而不是把它顶掉。

唯一一个真正意外的地方在**侧边栏**，不在后端。光归档并不能让退役的会话从活跃列表里消失：`/api/projects` 确实已经不返回它了，但 `mergeExpandedSessionPages` 只要发现新返回的会话数比前一次状态里少，就会把客户端已经加载过的会话再塞回去——这是给分页翻页做的保护，顺带也把一个本该离开的会话保了下来。所以靠重新拉取是修不好的，实测就是这么错的。退役会话的 id 改成搭在已有的 `SessionEstablishedContext` 上（新字段 `retiredSessionId`），由 `registerOptimisticSession` 在插入接替它的那个会话的**同一次** `setProjects` 里把它删掉——这样是原子的，两者连一帧都不会同时出现在列表里，而且不需要新增任何 prop 透传。

刻意没有处理的一点：空会话去请求 `GET …/token-usage` 会拿到 404，因为它还没有 provider 会话，浏览器控制台会记一条。前端本来就把非 ok 的响应当作「没有 token 预算」处理，用户看不到任何异常；只是 Clear 是第一条「在任何 run 发生之前就已经有会话 id」的路径，才让它显形。

议题 [#25](https://github.com/wltiger/my-cloudcli/issues/25) 给 Claude 加上 **Rewind**——同样先看 `CONTEXT.md` 的术语表。两个决定决定了它的全部形状。第一个是 ADR 0006：`resumeSessionAt` 是*下一次 query* 上的一个选项，不是一个独立操作，所以这里**刻意没有「已回退但还没发送」这种状态**。点了 Rewind 只是把那条消息重新装回输入框、把它以及它之后的内容变暗、并在输入框上方给一条提示；**真正执行 Rewind 的是按下发送**，而刷新页面会把一次还没发送的 Rewind 取消掉。持久化一个待用 anchor 的方案考虑过并被否决了——不要再加回来。

Anchor 规则是跟 Fork 并列的**第二条具体规则**，刻意不做成 Fork 那条的泛化——同一个 provider、同一种手势形状，落到的行却不同。`forkSession` 包含一轮对话的**最后**一行；`resumeSessionAt` 包含它**点名**的那一行，所以「退回*到*某条消息」意味着 anchor 落在它**前面**那一行。`claude-rewind.ts` 里的 `buildClaudeRewindAnchorIndex(rows)` 沿 `parentUuid` 链去找那一行，而不是按文件顺序找，因为一轮对话的行是跟 tool result 交错写入的。三个实测事实决定了这段走法：(1) 只有 **user** 行拿得到 anchor，因为 Rewind 只在读者自己的消息上提供——这点跟两侧都提供的 Fork 不同。(2) 这段走法会跳过 SDK 自己的 reader 不会返回的行：在本机全部 transcript 上实测，591 条用户提问里有 19 条的直接链父节点是 `attachment` 行（粘贴的图片或拖进来的文件会单独写成一行，紧挨在它所属的提问前面），还有 1 条是 `system` 行——落在这两种行上等于给 `resumeSessionAt` 一个它找不到的 uuid。(3) 最后一个压缩边界及其之前的行一律不给 anchor，这同时覆盖了边界之后的第一条提问（它整条链都在边界之上）和会话的第一条提问（前面根本没有行）——正是这个事实让 Clear 无法表达成一次 Rewind（ADR 0005）。

第二个决定是 ADR 0007，也是**分支过滤必须在这张票里一起做**、而不能留到后面的原因。一次 Rewind **不会**重写 transcript——它把 transcript 变成了一棵树。在真实的已回退会话上直接验证过：新一轮对话被追加到同一个文件里，`parentUuid` 指回 anchor，两条分支在物理上都还在，CloudCLI 的平铺 reader 会继续把被放弃的那条画出来，所以不过滤的话，这个功能**每次刷新**都会有一个肉眼可见的「旧消息又回来了」的 bug。SDK 有一个能识别分支的 reader `getSessionMessages`——注意它返回的是普通的 `Promise<SessionMessage[]>`，**不是** async iterable——但它同时会丢掉压缩边界之前的所有内容，那会把边界标记（本条目 #19 那一段做的）连同它上面的全部历史一起从屏幕上抹掉。所以 `filterClaudeAbandonedBranchRows(rows, activeRowUuids)` **只过滤最后一个边界之后**的那一段；边界之前的部分照旧平铺渲染。这样做之所以安全，恰恰是因为来自 Compact 之前的 anchor 根本无法解析，所以那里不可能存在被放弃的分支。

这个过滤器最吃紧的一点是**哪些行才允许被丢掉**。`getSessionMessages` 只返回 `user`/`assistant` 行，会丢掉 meta、sidechain 以及其他所有类型（`attachment`、`ai-title`、`last-prompt`、`queue-operation`、`mode`、`system`）。它们不在 active 集合里这件事，本身并不说明它们在哪条分支上，所以只有「SDK 本来就会返回」的行才有资格被丢——把单纯的「不在集合里」当成被放弃，会悄悄删掉读者的附件和子 agent 输出。集合**为空**表示分支没读出来，此时什么都不过滤，因为丢掉整段对话远比让一条废弃分支留在屏幕上更糟。还有一个实测出来的、差点踩中的坑值得记下来：并行工具调用会让一份**从没被回退过**的普通 transcript 也真的分叉——一条 assistant 消息发起两个工具调用时，每个 tool result 都被写在它那两个 `tool_use` 行中间，所以本机 102 个会话里有 68 个存在共享同一个 `parentUuid` 的行。`getSessionMessages` 把它们**一条不漏**地解析对了（逐行核对过），这正是过滤器安全的前提；自己手写一个单链走法会悄悄把这些轮次砍掉一半。

在本机全部 103 份 transcript 上扫了一遍，其中 94 份**完全没有变化**。有变化的 9 份里，被丢掉的行确实都不在 active 链上：明确的废弃分支，以及走到死胡同的 assistant 行（一次失败的「API Error」轮次；一次被同一个父节点下的 `system` 行接管了链路而作废的轮次）。有一点要当成**可见的行为变化**而不是无副作用的改动记下来：在 CloudCLI 之外被回退过的会话——Claude Code 自己的 CLI 做的就是同一件事——现在也不会再显示它们的废弃分支了，而以前两条都会显示。

前端这边 `supportsRewind` 完全照搬 `supportsCompact`/`supportsFork`/`supportsClear` 的先例，包括「后端确认之前一律为 false」这条规则，并且刻意**跟 `supportsFork` 分开**：OpenCode 今天能 fork，但要到 #26 才能 rewind，合并成一个标志就会给出一个点了没反应的入口。`NormalizedMessage` 新增第二个可选字段 `rewindAnchor`，而不是复用 `anchor`——两个操作、两行、对前端都同样是不透明的 token，前端依然一条 provider 规则都不持有。输入框那部分被拆成同一个 fork 自有文件里的两个 hook，纯粹是因为 **hook 顺序**：`useSessionRewind` 必须跑在 `useChatComposerState` *之前*，它的 Anchor 才能跟着发送一起走；而 `useRewindComposerPrefill` 必须跑在它*之后*，因为它要写的那些 setter 到那时才存在。附件跟文本一起回来——Claude 把用户轮次里的图片以 base64 内联持久化，所以最常见的情况完全不用走网络（`fetch` 直接读 data URL），存起来的非图片文件则回退到 asset store。用真实图片验证过：两个附件都逐字节还原（85 和 98 字节，MIME 正确，其中合法的那张在输入框缩略图里按 32×32 渲染出来）。

**退出回退时，输入框会被原样还原。**发起一次 Rewind 是破坏性的——它会覆盖读者正在输入的任何内容，附件也一样——所以 `useRewindComposerPrefill` 会在应用草稿的那一刻把输入框里原有的内容存下来，取消时再还原回去。没有这一步的话，一个写到一半的读者点开 Rewind 想看看自己之前说了什么、然后按 Esc，他自己的草稿就没了，而且没有撤销；这是实打实的数据丢失路径，不是观感问题，也跟本票自己写的「Esc 退出，视图恢复原状、什么都没变」相矛盾。有两个细节让它成立。存档是在**应用草稿的那个 effect 内部**读的，因为在那一帧输入框里还是读者自己的文本；而实时的值通过一个由独立 effect 同步的 ref 送进去，这样应用逻辑才不会在每次敲键时重跑。以及**只有取消才还原**——发送同样会让草稿消失，但发送已经把输入框清空了，此时还原等于把它重新填满。这就是为什么 `useSessionRewind` 暴露的是一个朴素的 `clearRewind`（供发送路径和切换会话时的重置使用），而带还原的 `cancelRewind` 是**由 `useRewindComposerPrefill` 返回**、只接到提示条的 Esc/✕ 上。不要把这两个函数合并：提示条上接错会静默地把草稿丢失重新引入，发送路径上接错则会把刚清空的输入框重新填满。这里什么都不持久化，所以刷新依然会取消一次从未发送的 Rewind，也不还原任何东西（ADR 0006）。这次存档/还原顺带修掉了另一个 bug：应用草稿时现在**无条件**调用 `setAttachedFiles(files)`，而不再是只在非空时调用，所以回退到一条本来没有附件的消息时，会把输入框里原有的附件清掉，而不是让它们搭车一起发出去。

有一个行为是刻意如此、不要顺手「修掉」的。**run 进行中时入口是隐藏的**（`!isProcessing`），这顺带覆盖了它跟 Fork 共有的那个真实缺口：实时流式消息不带 anchor，因为一轮对话的 anchor 要等它的 transcript 行落盘才知道。和 Fork 一样，这个缺口靠 sessions watcher 自愈，不需要额外代码。Rewind 是**单条消息上的控件，不是斜杠命令**，所以它刻意完全不碰 `executeCommand` 的拦截分支，也不碰 skill/compact 那个「原样发给 provider」的放行名单。

在真实 Claude 会话上端到端验证过：一段三轮对话从中间那条消息回退后，在**同一个会话 id** 下继续，被放弃的那几轮从消息流里消失，而且——这是本票的关键——**刷新之后依然不见**，与此同时磁盘上的 transcript 里它们还实实在在挂在一个有两个子节点的父节点下面。另有一个跑过两次 `/compact` 的会话，边界之前的历史和它的 `Compacted · 47,256 → 3,272 tokens` 标记都照常渲染，并且整个会话里 Rewind 入口是**零个**。入口出现在 3 条用户消息中的 2 条上（第一条前面没有行），在所有 assistant 消息上都不出现，并且在 run 期间降到 0。

工单 [#26](https://github.com/wltiger/my-cloudcli/issues/26) 收尾这一组，做的是 **OpenCode 上的 Rewind**，也是这一组里唯一一个会动到读者代码的手势。OpenCode 没有 `resumeSessionAt`，它有的是 `POST /session/{id}/revert`：把会话退回去的同时，**还会把被 git 跟踪的文件恢复到那个时刻的内容**——实测，调用一返回，一个被跟踪的文件就从 `hello v3` 变回了 `hello v2`。一次 Rewind 会不会动文件，是由 provider 定死的，不是给用户选的（见 `CONTEXT.md` 里的 Rewind 词条），所以这里没有开关：能力矩阵多了第二个标志 `rewindRestoresFiles`，它唯一的作用就是让输入框上方的提示条在读者按下发送**之前**把这件事说清楚。那多出来的一行提示，就是前端改动的**全部**——其余部分（入口、变暗、预填、Esc、取消还原输入框）本来就与 provider 无关，一行都不用改。

Anchor 规则是**第三条**具体规则，而且它跟同一个 provider 上的另外两条彼此矛盾。`opencode-rewind.ts` 里的 `buildOpenCodeRewindAnchorIndex(rows)` 把一条用户消息映射到**它自己**，因为 revert 是*包含式*的——点名哪条消息，就连那条一起往后全部丢掉。而它自己的 fork 是*排除式*的，所以 `buildOpenCodeAnchorIndex` 会把同一条消息映射到**下一轮**的第一条消息，位置还要往后一格。同一个 provider、同一个手势形状、相反的约定；这就是"Anchor 必须是各 provider 自己的不透明 token"最实在的证据，三条规则必须各自能分开读懂，绝不能合并成一条。跟 Claude 的规则还有两处刻意的差别：同样只有用户消息才有 anchor，但**这里会话的第一条提示词也有** —— Claude 的规则锚在消息*前面*那一行，第一条提示词前面没有行，而 revert 点的就是消息本身，所以对开头那条提示词做 Rewind，含义就是"清空会话并把所有文件一起退回去"，这是完全合理的诉求。另外，最后一次 compaction 及其之前的所有消息一律没有 anchor，跟 fork 索引用的是同一条保守规则；这一条在这里承担双重作用：下面那个过滤器拒绝碰那一段，所以如果那里给了 anchor，服务端会真的 revert，而界面上被 revert 掉的消息一条都不会少。`opencode-anchors.ts` 现在导出了 `readOpenCodeMessageIndex`（以及行/摘要两个类型）——这一次扫描把按 part 拆开的行合并回消息，并找出最后一次 compaction ——三条规则共用它，跟 `claude-anchors.ts` 把 `findLastCompactBoundaryIndex` 导出给 `claude-rewind.ts` 是一模一样的做法。`buildOpenCodeAnchorIndex` 改成基于它实现，行为没有任何变化，它自己的测试一行没动，照样通过。

**过滤历史在这里同样是 CloudCLI 的活**，这一点必须直说，因为 #25 留下的结论正好相反（"既然 `revert` 是服务端改数据，OpenCode 就不需要分支过滤"）。对着真实的 1.18.18 服务重新量过，那个结论是错的：revert 之后，`GET /session/{id}/message` 依然返回一个七条消息会话的**全部七条**，`opencode.db` 里七行也一行没少。变的只是 session 行上的一个字段 —— `revert`，里面装着 `{messageID, snapshot, diff}` —— `filterOpenCodeRevertedRows` 读的就是它，并且按 ADR 0007 只在最后一个 compaction 边界之后生效，跟 Claude 那个过滤器完全一致。没有它，这个功能就会带着 #25 存在的意义所在的那个可见 bug 上线：一刷新，旧消息全回来了。`revert` 是 `session` 表建表时就有的字段（不是后面 `ALTER` 追加的那批），所以读它不用像 token 计数那样先做 `PRAGMA table_info` 保护。

有两点决定了它是**两次调用而不是一次**，这也正是它没办法像 Claude 的 anchor 那样搭 `buildSendOptions` 便车的原因。`resumeSessionAt` 是一次查询上的选项；`revert` 是一个必须发生在发送**之前**的、独立的即时操作。所以 `spawnOpenCode` 做了拦截：`readOpenCodeRewindAnchor(options)` 读的就是前端本来就会发过来的那个 `resumeSessionAt` 字段（websocket handler 会把客户端传来的未知选项原样展开，所以它是白搭车过来的），`runOpenCodeRewindSend` 先执行 revert，然后把 Anchor **摘掉**再重新进入 `spawnOpenCode` —— 摘掉这一步就是防止同一个分支被走第二次的全部机制。revert 和撤销 revert 都是启动并关闭 Compact（#21）和 fork（#23）用的**同一个**短命 headless `opencode serve`，绝不会有第三个，各自的 `finally` 在成功、失败、抛异常时一律把它杀掉。"OpenAPI 文档是错的"这条教训第三次生效，而且这次是重新量过而不是照搬：`POST /api/session/{id}/revert` 根本不是一条路由，会落到 Web UI 的 HTML 兜底上，**返回 200 和一段 HTML**，而什么都没做——那个本该被回滚的文件原封不动。只有从旧的无前缀路由的**响应体里**读出被记录下来的 revert，才能证明它真的执行了。

恢复路径是实测推翻了原设计的地方，后面也不要"顺手简化"掉。工单的前提——发送在 revert 成功之后失败时，调 `unrevert` 把对话**和**文件都放回去——对**独立的一次** revert 是成立的：直接量过，`unrevert` 两样都恢复了，字段也清了。但发送一旦开始，它就**不**成立了，因为 `opencode run` 只要把自己那条用户消息追加进去，就会**落定**一次尚未落定的 revert：被 revert 掉的消息被物理删除，`revert` 字段被清空——而这发生在绝大多数失败来源（模型调用）之前。这种情况下再调 `unrevert`，它照样返回 200、`revert` 为空，跟"确实恢复了"完全分辨不出来；这段代码的第一版就是这样一边让 `tracked.txt` 停在被回滚的内容上，一边高高兴兴地告诉读者"文件已经放回原处了"。所以 `undoOpenCodeRewind` 会先读一次 session，只有**仍然停在这个 Anchor 上**的 revert 才去撤销；否则就如实相告——早先那些消息已经没了，文件还停在回滚后的位置。这里静默恢复不可接受，但**谎称**恢复了更糟，而只有那一次读取能把两者分开（ADR 0009；也正是这次读取，决定了读不出来的 session 要报成「状态未知」而不是「已落定」）。这一点对上面那个过滤器还有个实际推论值得记住：既然发送成功就会让 revert 落定，CloudCLI 真正需要过滤的窗口是**尚未落定**的那一种——在 OpenCode 自己的 TUI 里做的 revert，或者发送失败/被中止的那一次。这个状态下实测过：provider 自己的接口返回全部 8 条消息，而 CloudCLI 的消息流只显示存活下来的 11 条渲染消息，刷新前后都一样。

有一个刻意留下的缺口：**revert 进行中的那 1～3 秒里没法按停止**，因为 CLI 还没被拉起来，`activeOpenCodeProcesses` 里什么都没注册，`chat.abort` 在这个窗口里会回 `NO_ACTIVE_RUN`。Compact 出于同样的原因注册了一个占位句柄；Rewind 没有，因为它这个窗口自己会关上，紧接着正常的 run 就把自己注册进去了。要补上是一个新决定，不是漏了一行。

对着真实的 OpenCode 1.18.18 会话、在一个 git 工作区里端到端验证过。入口出现在两条用户消息上、assistant 消息上一个都没有；提示条显示的是 *"Sending will take the conversation back to this message. 6 messages leave the context."*，紧跟着 *"Tracked files will be rolled back to their state at that message too."*；按下发送后 `tracked.txt` 从 `hello v3` 回到 `hello v2`，会话**保持同一个 id** 继续。在故意留下一个未落定 revert 的状态下刷新，被 revert 的提示词在消息流里消失了，而 OpenCode 自己的接口依然把它返回。用一个解析不了的模型强制发送失败，读者拿到的是如实的那句话而不是好听的那句，跟磁盘上的文件状态一致。同一个会话在真的跑过一次 `/compact` 之后，边界之前的历史全部照常渲染、`Compacted` 标记完好，并且**一个** Rewind 入口都不提供——因为每条用户消息都在边界之上。
