# 同步官方源码操作指南

把 `siteboon/claudecodeui`（`upstream`）拉取合并进本 fork（`wltiger/my-cloudcli`，`origin`）的具体步骤。跟 `docs/fork-customizations.md` 配套——那份文件记录"哪里不一样、为什么不一样"，这份文件记录"具体怎么操作"。反方向——把 bug 或者缺口反馈给 upstream——看 `upstream-pr` 这个 skill / `docs/upstream-pr.md`；这份文件只管往里拉。

远端/分支的完整配置（`main` 镜像 `upstream/main`，所有 fork 工作都在 `dev` 分支上）在 `docs/agents/issue-tracker.md` 里有完整记录，这里默认那套配置已经搭好。

## 开始之前

- `dev` 分支 `git status` 是干净的——手头有没提交的改动先 commit 或者 stash。
- 确认 `git config rerere.enabled` 是 `true`（不是的话跑 `git config rerere.enabled true`）——它会自动重放这个仓库之前已经解决过的冲突，同一批自定义文件反复冲突只会越来越省事，不会越来越麻烦。

## 1. 预演一遍合并（每次都要做，第一步）

```
git fetch upstream
git merge-tree --write-tree dev upstream/main
```

纯只读——不碰工作区、不碰 index、不碰 HEAD（会往 `.git` 里写几个没有引用的对象，无害，之后会被垃圾回收）。它会报出如果现在把 `upstream/main` 合进 `dev`，具体哪些文件会冲突——不用照着 diffstat 猜。退出码是 `1` 说明有真实冲突；输出里既列出每个冲突，也列出所有合并干净的文件。

**每次都做**，不管这次同步看起来多小——这一步几乎不花时间，而且下面第 2 步和第 5 步都要用它的结果。

## 2. 决定：直接在 `dev` 上做，还是先开个临时分支

看第 1 步给出的冲突清单。

- **小同步**——真实冲突大概 ≤2-3 个文件，而且没有一个涉及退休/改造某个 fork 定制项（只是照着定制项已有的冲突处理指引重新套一遍）→ 直接在 `dev` 上合（跳到第 3 步，下面提到"临时分支"的地方都换成 `dev`）。
- **大同步**——冲突文件更多，或者只要处理其中任意一个就要退休/改造某个定制项而不只是重新套用指引 → 先开一个临时分支（`git checkout -b sync/vX.Y.Z dev`），把 `upstream/main` 直接合进**这个分支**（不是本地 `main`——`main` 保持旧状态，等落地那一步再更新，见第 5 步），所有解决和验证都在这个分支上做，全部跑通、审核过之后再把 `dev` 快进到它。中途出问题就直接删掉这个分支，`dev` 完全没受影响。

这是个需要判断的事，不是死规则——拿不准的时候就开临时分支；多开一个分支的成本，比把 `dev` 卡在一个半解决的状态里低得多。

**临时分支上的 git 权限**：可以自由 commit，不用每次都问——反正是一次性的，而且在你明确"落地"之前不会碰 `dev`/`main`/任何远端。落地到 `dev`/`main`，以及任何 `git push`，还是要各自单独确认，跟平时一样。如果你对某次同步有别的明确要求，按你说的来，不用照这个默认走。

大同步可以考虑在动手解决任何冲突之前，先按子系统拆出几个并行的研究 agent（比如按互不相关的冲突文件簇分组）——每个都拿到第 1 步验证过的冲突清单，加上相关的 `fork-customizations.md` 词条，回来给出每个文件的处理建议。比一个 agent 从头到尾顺着查要省，而且每个子系统的上下文都更聚焦。

## 3. 更新干净镜像分支

如果在临时分支上做，跳过这步——`main` 保持不动，等第 5 步再更新。

```
git checkout main
git pull upstream main
```

`main` 应该能干净地 fast-forward——它上面从来不放本地提交。如果不能 fast-forward，说明有东西误提交到了 `main` 上，先处理这个问题（正常使用下不应该出现）。

## 4. 合并进工作分支

```
git checkout dev
git merge main
```

（如果在临时分支上，这一步在第 2 步已经做完了——直接合并的是 `upstream/main`。）

用真正的 merge，不要用 rebase——这个工作分支已经 push 到 `origin` 上了，每次同步都 rebase 意味着每次都要强推、重写共享历史，这里没有实际收益。用 merge 还能留下"每次官方更新具体是什么时候合进来的"这个诚实的记录。

## 5. 逐个文件解决冲突

第 1 步列出的每个冲突文件：

- 先查 `docs/fork-customizations.md`——这个文件是不是在里面某一条编号的自定义清单里？
  - **是** → 按下面顺序判断属于哪种情况：
    1. **原样重新套用。** 大部分条目都是"保留我的，在官方新代码外面重新套一遍条件判断/包装"——照做就行。
    2. **先重新评估，再决定。** 有几条明确标了这个（目前是第5、6条）——处理这几条之前先读一下链接的 ADR，或者重新过一遍当时的推理，不要无脑照搬上次的处理方式。
    3. **退休或者改造。** 如果 upstream 这次的改动看起来是从根本上解决了这个定制项当初要解决的同一个问题，不要因为词条上写着"保留我的"就默认继续保留——那句话是在这次 upstream 改动出现之前写的。要判断：upstream 这版是不是让这个定制项完全变得多余了（**退休**——删代码，词条标成已退休，词条本身不删）；还是只让一部分变得多余（**改造**——只留下还有独特价值的那部分，比如一个单独的入口，upstream 已经覆盖到的那部分就删掉）；还是 fork 自己的实现是**替换**而不是**合并**upstream 的数据/行为（如果是这样，原样保留就不是个中性的选择，是倒退——会把 upstream 新加的、fork 版本没有独立实现的东西悄悄丢掉）。这几种情况该怎么定，要问你，不要自己单方面决定——除非是特别显而易见的小事。
  - **否** → 这是一个目前没被记录在自定义清单里的意外冲突。先按自己的判断解决掉，然后想一下：这只是一次偶然的、无关紧要的碰撞（不用记），还是暴露了一个真实的、会长期存在的分歧（应该补进 `fork-customizations.md`）？如果是后者就补一条。
- `git rerere` 会自动把之前见过的、一模一样的解决方案重新贴上去——用 `git diff --staged` 看一眼它做了什么，不要盲目信任，尤其是如果官方那边这次改动幅度比上次大很多的话。

**两边都改过、但 git 判定"没冲突"的文件也要查**（第 1 步输出里除 `CONFLICT` 之外的部分）——合并干净只代表两边改的行没有物理重叠，不代表结果在逻辑上是对的。特别留意两种已知的翻车方式：

- **重复注册。** 两边在同一个"概念槽位"上都加了东西（一个路由、一个事件监听、一个导出），但插入的物理位置不一样，git 就看不出重叠。框架跑起来的时候只会用其中一个（比如 Express 匹配两个路径相同的路由里的第一个）——不报错，就是悄悄地行为不对。路由表、注册表这类"按名字/路径查 handler 的列表"文件风险最高。
- **改名只改到了一边。** upstream 把一个共用的符号（常量、类型）改了名字；git 会把这个改名应用到 upstream diff 涉及的每一行，但 fork 自己加的、引用旧名字的那一行——如果不在任何冲突区块里——不会被动到，就悄悄地过期了。如果旧名字彻底不存在了，`npm run typecheck` 能抓出来；如果改成了另一个碰巧也能编译通过的名字（比如一个仍然合法但语义错了的字符串字面量），typecheck 抓不出来。

## 6. 验证

```
npm install        # 万一依赖变了
npm run typecheck
npm run lint
npm test
```

然后把手动浏览器走查这一步交给你自己，不用我尝试全部走一遍——按风险从高到低分三层列清单：

1. **这次退休或者改造过的东西**——最可能出真回归的地方，因为这是新代码，不是照搬原有模式。
2. **upstream 新功能里跟某个定制项碰到同一个子系统的地方**——确认能正常共存（没有视觉/功能上的打架），哪怕这次完全没冲突。
3. **upstream 这个版本自己修的 bug**——优先级低一些，条件允许的话顺手看一眼。

（固定测试账号的用法见 `.claude/CLAUDE.md` 的"Local UI testing"那节，把这个交给你自己走查时用。）

## 7. 落地并推送

**直接在 `dev` 上做的同步：**
```
git commit          # 只有合并本身需要解决冲突才用提交
git push origin dev
```

**临时分支的同步**，验证通过、审核过之后：
```
git checkout main && git merge upstream/main   # fast-forward，第 3 步延后到这里做
git checkout dev && git merge sync/vX.Y.Z      # fast-forward，因为 dev 一直没动过
git branch -d sync/vX.Y.Z
git push origin main
git push origin dev
```
每次 push 还是要单独确认，跟平时一样。

## 同步完之后：回头看一遍 fork-customizations.md

有几条自定义之所以存在，就是因为当时官方**还没解决**那个问题（离线缓存、命名不统一等等）。每次同步完，把清单过一遍：官方是不是刚好上了什么功能，让某条自定义整个变得多余了？如果是，就把那条自定义的代码和清单条目一起删掉，不要背着一个已经没用的分歧继续走下去。如果某条的原因变了但自定义本身还需要保留，就把它的"为什么"/"同步时怎么办"文字更新一下，不要留着过时的说法。

然后想一下这次同步过程中发现的东西——一个 bug、一个设计缺口、一个经过验证的技术结论——值不值得反馈给 upstream。如果值得，用 `upstream-pr` 这个 skill（`docs/upstream-pr.md`），不要自己从头起草。
